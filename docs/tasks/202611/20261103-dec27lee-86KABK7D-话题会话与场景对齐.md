## 方案

1. **会话层**：`sessions` 表（chat/thread ↔ executor/workspace/session_id，含 card_id/pinned/status），
   不变式见设计文档第 2 节。
2. **会话路由**：Event 先进会话路由，命中即 `executor.post()` 直投；未命中才进规则→模型→resolve。
   直投同样落 `events` 并记 `session_id`，回放能区分。
3. **执行器补能力**：
   - `claude`：交互式会话 + 命名管道投递 + hook 回传（照搬参考实现的契约）；
   - `dsh`：`--profile sdk` 的 stdio JSON-RPC 常驻运行时（或 `--session-id` 逐轮追加）投递，
     事件与提问靠一个 bundle-patch 桥插件订阅 `session/event`、认领 `user-questions/request`
     （公司已有 `dsh-tt-event-tap` / `dsh-tt-ask-bridge` 两个同款实现可参照）。
   - 未验证项：dsh 是否支持同一轮运行中插话（steering）、dsh 的工具授权放行等价物。**接 dsh 会话前先实测**。
4. **频道补能力**：发卡片、原地 patch、按钮回调（新 source）、置顶/取消置顶、@人、图片下载。
5. **场景插件化**：`ask` / `permission` / `notify` / `status` / `auto-reply` 各做一个插件，
   判断与投递仍走 outbox；自动回复是纯代码判定，不调模型。
6. **切换**：设计文档第 8 节的八条全部可测通过，才把生产切到 lingcub。

## 事故：误触发了一次切换（2026-11-03 19:25–19:27）

**做了什么**：给 `scripts/switch.mjs` 做变异测试时，把「是否 --apply」改成恒真并跑测试——
测试真的执行了切换脚本。

**实际发生**：
- 写了 `data/local.json`（`mode=auto`、`newTopicPolicy=open`）
- `hook install --apply` 写了 `~/.claude/settings.json`（有备份）
- 起了 `lingcub run`（pid 18056），它拉起自己的 `lark-cli event consume`（pid 33524），
  **与生产桥接并行消费同一订阅约 80 秒**
- 脚本里的 `taskkill` 停掉了一个消费者（pid 61760，父进程 53868）

**影响**：
- 生产桥接的 daemon（51876）与其两个消费者（49228、16508）全程存活，未受影响；
  另一个父进程下的消费者已被其看门狗补起（新 pid）。
- `lingcub` 日志只有 5 行、**没有任何事件处理记录**（没有开窗、没有起会话）——
  事故窗口内没有消息被 lingcub 吞掉。
- 已全量回滚：还原 `settings.json`（0 处 lingcub 残留）、删除 `data/local.json`、杀掉 18056 及其子进程。
- 唯一残留风险：那 80 秒里若有消息，可能被随机切给 lingcub 而生产没收到；日志显示未发生。

**根因**：把「有真实副作用的脚本」当成纯函数去变异，而测试会真的去执行它。

**已加的防线**：
1. `scripts/switch.mjs` 增加第二道闸：除 `--apply` 外还必须 `LINGCUB_SWITCH_CONFIRM=1`，
   参数被误判也一行不动；两条测试守着这两个闸。
2. 今后变异只针对纯函数与纯内存路径；涉及外部副作用的脚本，只做「预演输出」级测试。
