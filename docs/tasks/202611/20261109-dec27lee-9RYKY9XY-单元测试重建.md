## 1. 需求描述

### 1.1 现状

- 测试全平铺在 `test/`：**126 个 `.test.ts` + `test/golden/` 4 个夹具文件**，无子目录、无场景登记、无执行产物。
- 执行入口只有一条：`package.json` 的 `test` = `node --experimental-strip-types --test test/*.test.ts`。
- 基线（迁移前实测）：`pnpm test` → **612 pass / 0 fail / 19.9s**。
- 归属靠文件名猜：`store.test.ts` 是内核，`doc-write.test.ts` 是领域，`e2e.test.ts` 是整链，没有机器可读的域、层级、优先级。

### 1.2 目标

参考 tongclaw 的 `tests/` 治理方式重建本项目单元测试的组织与执行面，**不重写断言**（既有判据是资产）：

1. `test/` 更名为 `tests/`，按**被测模块域**分目录，一眼看出这条用例属于哪一层。
2. 每个域一份 `case.md`（人工评审：这层管什么、不管什么）+ `suite.yaml`（执行真相：每条用例的 ID／层级／优先级／状态／单跑命令／断言点）。
3. 补统一 runner：可按域、按用例 ID、按标签／优先级执行，结果落 `tests/out/<runId>/`（`summary.json` + 单条日志 + JUnit）。
4. 保持 `pnpm test` 一键全量，且默认全绿、无外部依赖。
5. 规范正文落 `tests/README.md`，与项目既有文档分工一致。

### 1.3 非目标

- 不改业务代码（`src/**`）、不改任何断言语义；只允许因目录深度变化修正**导入路径与仓库根定位**。
- 不引入测试框架：仍是 `node --test`（`AGENTS.md` 硬规则）。
- 不照搬 tongclaw 的 Playwright／UI／登录态／bootstrap（本项目没有前端服务与登录态）；只借其**目录职责、场景登记、状态三档、产物口径**。
- 不做 tongclaw 的 `env.example`／`.env.local`：本项目单元测试不需要外部凭据。

## 2. 技术设计

### 2.1 目录定型

```text
tests/
  README.md                  规范正文：目录职责、编号、状态、执行、产物、判据
  scenarios/<domain>/
    case.md                  人工评审入口：域职责、覆盖规则、不覆盖项、判据来源
    suite.yaml               执行真相：runner 只读这里
  specs/<domain>/*.test.ts   用例实现（按被测模块归域）
  support/                   共享夹具（golden 的 cases/harness/baseline/capture）
  scripts/                   runner 与公共库（node 脚本，非测试）
  out/<runId>/               结果产物（git 忽略）
  .runtime/                  本地运行态缓存（git 忽略）
```

### 2.2 域划分（9 个，按 `src/` 边界）

| 域 | 前缀 | 对应 `src/` | 判据 |
| --- | --- | --- | --- |
| `domain` | `DOMAIN` | `src/domain/**` | 四层模型与纯规则（doc-xml、doc-todos、ids、card-action…） |
| `kernel` | `KERNEL` | `src/kernel/**` | 内核不变式（store、outbox、event-log、capabilities、plugin-v2…） |
| `routing` | `ROUTING` | `src/routing/**` | 三级漏斗、规则谓词、命令解析、自动回复 |
| `plugins` | `PLUG` | `src/plugins/**` | 单个插件的行为（频道／源／场景／执行器／能力） |
| `plugin-kit` | `KIT` | `src/plugin-kit/**` | 插件共用工具（claude/dsh 探测、cc-switch、spawn、模板…） |
| `desktop` | `DESK` | `src/desktop/**` | 桌面窗口与服务端、UI 目录、插件注册 |
| `flow` | `FLOW` | 跨域 | 真内核 + 假端口的整链（e2e、装配类） |
| `golden` | `GOLDEN` | `src/kernel/pipeline` 等 | 金标逐字对拍（`support/golden/` 夹具） |
| `ops` | `OPS` | `scripts/**` | 运维脚本（切换、看门狗、自启、钩子安装） |

归域判据：**按被断言的主体**归域，不按 import 最深的模块。example：`session-open.test.ts` 断言 `capabilities.submit` → `kernel`；`bus-entry.test.ts` 装配三个插件跑整链 → `flow`。

### 2.3 场景编号与层级

- 编号：`<PREFIX>-<LAYER>-<NNN>`，如 `KERNEL-UNIT-004`、`FLOW-E2E-002`、`GOLDEN-INT-001`。
- `layer`（只三种，本项目事实）：
  - `unit`：纯函数／纯内存／临时目录，单文件毫秒级。
  - `integration`：真内核（Store/Outbox/EventLog/Pipeline）+ 假端口或假 CLI，单文件秒级。
  - `e2e`：起真进程或真 CLI 壳（`lark-cli`/`claude` 的假可执行文件）走完整链路。
- `priority`：`P0` 内核不变式与架构约束／`P1` 其余单元／`P2` 依赖本机环境的探测与安装类。
- `status`：`ready`（默认 smoke，无外部依赖）／`gated`（需本机真实安装或凭据，默认不跑）／`pending`（仅有设计）。**只有真跑不动才标 gated**，当前基线 612 全绿，故默认 ready。

### 2.4 suite.yaml 字段（相对 tongclaw 的本地化）

```yaml
suite: kernel
domain: kernel
scenarios:
  - id: KERNEL-UNIT-001
    title: 发件箱先标记后投递，崩溃后回到 pending
    layer: unit
    priority: P0
    tags: [kernel, outbox, unit]
    status: ready
    command: node --experimental-strip-types --test tests/specs/kernel/outbox.test.ts
    assertions:
      - 先 dispatched 再投递，成功才 done
      - 进程崩溃恢复时 dispatched 无条件回 pending
    sourceCaseIds: [KERNEL-RULE-01]
    timeoutSec: 60
```

去掉 tongclaw 的 `bootstrap`（无登录态）与 `cleanup`（每条用例自建临时目录）；保留 `sourceCaseIds` 用于回链 `case.md` 的人工规则编号。

### 2.5 执行入口

| 目的 | 命令 |
| --- | --- |
| 全量（CI／收尾） | `pnpm test` |
| 单域 | `pnpm test:suite --suite=kernel`（= `node tests/scripts/run-suite.mjs --suite=kernel`） |
| 单用例 | `pnpm test:case --case=KERNEL-UNIT-001` |
| 标签／优先级 | `node tests/scripts/run-suite.mjs --tag=outbox`、`--priority=P0` |
| 列清单 | `node tests/scripts/run-suite.mjs --list` |

runner 约束：**cwd 固定为仓库根**（测试里多处用 `process.cwd()` 建临时目录、读 `config/rules.yaml`）；只读 `tests/scenarios/*/suite.yaml`；不通过 `suite.yaml` 的用例不执行（防「只是新增了 spec 没登记」）。

### 2.6 迁移期必须修的路径引用（机械改动，不改语义）

| 位置 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 用例 import | `from '../src/...'` | `from '../../../src/...'` |
| 仓库根定位 | `resolve(import.meta.dirname, '..')` | `resolve(import.meta.dirname, '../../..')` |
| 夹具相对引用 | `./golden/cases.ts` | `../../support/golden/cases.ts` |
| 外部扫描 | `readdirSync('test')` | 递归 `tests/specs` |

### 2.7 验证口径

1. 全量：`pnpm test` **612 pass / 0 fail**（与迁移前同数），`pnpm build` exit=0。
2. 单域／单用例：`run-suite.mjs` 三段输出（列表／单跑／产物文件）真跑。
3. 变异反证：在 runner 与「未登记用例不执行」判据上做——改坏 runner 的筛选逻辑或删掉用例的登记行，必须真红。

### 第 2 轮：按本项目成本重写「测试范围约定」

**输入**：参考项目 `workspace/tongclaw/CLAUDE.md` 的测试相关章节——「测试范围约定（强制）」（103–156 行）与
前端测试目录二分（70–75 行）。

**那份规则为什么这么写**（读出的驱动因素）：

1. **成本驱动**：Maven Reactor + 前端 pnpm 全量是分钟级到十几分钟，开发迭代里跑全量会毁掉反馈循环，所以直接下禁令。
2. **模块隔离**：每个模块独立 `pom.xml`，`-f <module>/pom.xml -Dtest=类#方法` 能精确到方法，并用
   `-Dsurefire.failIfNoSpecifiedTests=false` 兜住拼错名字；`*IT` 由 failsafe 在 verify 阶段跑，不进日常流程。
3. **引用可枚举**：Java 静态依赖可枚举，所以「覆盖直接引用方」是有界范围。
4. **证据成本**：H2 通过不算验证，MySQL 方言要另取证据（Testcontainer 或 DBX `EXPLAIN`），全量还依赖外部环境。
5. **目录二分**：模块内单测固定单数 `test/`，根 `tests/` 只放 Playwright 系统级；禁止在 `src/` 下建 spec、禁止再建 `tests/`。

**本项目的差异（实测）**：全量 612 条 **17.5s**；单域 kernel 9.0s、plugins 6.6s；P0 组 6.1s；单条 0.7s。
量级差 1–2 个数量级，且插件是**动态装配**——「引用可枚举」不成立（改 `src/kernel` 等于改所有插件）。
因此保留其「定向」「全量兜底」的分工，丢掉其「禁止全量」，把全量触发条件从「引用可枚举」改成「跨域必跑」。
