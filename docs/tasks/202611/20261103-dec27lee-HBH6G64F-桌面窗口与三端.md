## 2026-11-04 排查：常驻进程静默退出

**现象**：飞书收不到本机 Claude Code 会话的结果通知，持续十余小时（最后一条入站事件 11-03 23:38）。

**根因**：常驻进程不在了——`data/lingcub.lock` 仍留 pid 64412，该进程不存在；钩子端口 63185 无监听。
钩子入口只读 `data/hooks.json` 后 POST，端点不在就写一行 WARN 到 stderr 后丢弃，**不会自动拉起常驻**，
所以 daemon 一停整条「飞书发起 → 本机执行 → 结果回飞书」链路静默中断，claude 侧只看到钩子非 0 退出。
日志停在 11-04 10:52:06，其后无输出也无崩溃堆栈，退出原因无法从日志判定。

**处置**：`wscript scripts\start-hidden.vbs run` 重新拉起（supervisor 53484 → main 7832，钩子端口 63969），
进程已跨命令边界存活。

**验证**：经真实入口 `node dist/main.js hook post stop` 向运行中的会话 `c510e321` 投递自检载荷，
outbox 两条（`card_send` / `card_upsert`）均 `done`、attempts=1，`cards` 表拿到真实消息 id
`om_x100b61ab77aeeca4`，session `last_stop_at` 同步更新——飞书侧确已收到。

**新发现缺陷（已在下一节修掉）**：`start-hidden.vbs` 不传 `run` 时，`supervise.mjs` 拉起的
`dist/main.js` 无参运行＝跑 `doctor` 后 exit 0，看门狗按「正常结束不重启」退出；
`install-autostart.mjs` 生成的 `lingcub.cmd` 同样不传 `run`，即**开机自启装上也不会拉起常驻**。
另外启动文件夹里从未装过自启项。

## 2026-11-04 P3.0-e：自启与子命令兜底

四条启动路径（`start-hidden.vbs`、Windows 自启、mac plist、linux unit）都经 `run-lingcub.sh`/`supervise.mjs`
把参数透传下去，空参就是空参。兜底只加在**看门狗这一层**，一处覆盖四条，新增启动路径也不会再漏：

| 改动 | 落点 | 为什么 |
| --- | --- | --- |
| 子命令缺省 `run` | `scripts/supervise.mjs` `resolveArgs()` | 空参时子进程只跑 `doctor` 后 exit 0，看门狗误判「正常结束」直接退；兜在一次，不必四处重复传 |
| Windows 自启改 `.vbs` | `scripts/install-autostart.mjs` `winTarget()` | 原来写 `.cmd` + `start /min`，登录后留一个黑窗口，与「常驻无窗口」冲突；`.vbs` 由 wscript 承载，窗口数为零 |
| 卸载连带旧 `.cmd` | 同上 `legacy` | 旧版装过 `.cmd` 的话，两份自启会抢着起 |
| 可测试化 | `isMain` 判断 + 导出 `winTarget`/`macTarget`/`linuxTarget`/`findRoot` | 原来整个脚本顶层就写盘，测试没法 import |

**验证**：`test/supervise.test.ts` + `test/autostart.test.ts` 定向 6 条绿；全量 255/255 绿；
`audit-parity` 30 功能 + 15 约定缺失 0、测试踪迹 30/30；`check-docs` 通过。

**变异反证**：`resolveArgs` 去掉默认 `['run']` → 定向测试红，还原绿；`.vbs` 窗口样式 `0` 改 `1` → 自启测试红，还原绿。

**真实演练**：装上入口（`node scripts/install-autostart.mjs --apply`）→ 停掉旧实例（53484/7832）→
直接用启动文件夹里的 `lingcub.vbs` 拉起，得到 supervisor 32588 → main 48744（`supervise.mjs` **无参数**，
子进程正确为 `dist/main.js run`）、锁 48744、钩子端口 61005、三来源启动，两个进程 `MainWindowHandle=0`（无窗口）。
卸载 `--uninstall --apply` 删掉入口、再 `--apply` 装回，两次都验过。

**残留风险**：登录时若已有实例在跑，新拉起的进程拿锁失败会 `exit 1`，看门狗按崩溃退避重试
（最长 300 秒一次），不致命但日志会留 ERROR；要根除得让「已有实例」以 0 退出。

## 三端入口（P3.0-d）

| 点 | 做法 |
| --- | --- |
| 定位项目根 | `scripts/launch-ui.mjs` 从自身位置向上找带 `@yue/lingcub` 的 `package.json`，目录挪位置也不断 |
| 复用实例 | 读 `data/ui.json`（port/token/pid），pid 活着且 `/healthz` 通就直接打开那个 URL |
| 起新实例 | 没有可用登记时分离进程起 `dist/main.js ui --no-open`（没构建则起 `src/main.ts`），轮询登记 + 探活最多 15 秒 |
| 三端壳 | Windows `lingcub-ui.cmd`；macOS/Linux `scripts/launch-ui.sh`（补 Homebrew/nvm/volta/asdf 的 PATH）；Linux 另附 `lingcub-ui.desktop` |
| 登记清理 | 面板关闭时只删自己写的那份（校验 pid），不误删别的实例 |

## 配置覆盖层（P3.0-c）

## 风险

- 单实例锁只做「pid 存活」判断（参考实现还校验命令行），pid 被复用时可能误拒；启动时会打印 pid，便于人工核对。
- 面板只读：改配置仍要编辑 `config/*.yaml` 并重启，P3.0-c 才补页内编辑。
- `lingcub run` 会真的拉起来源进程；本机已有生产 daemon 在跑同一订阅，**未做真连验证**（同一订阅并行会随机切分事件）。
