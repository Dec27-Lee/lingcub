## 1. 需求描述

### 1.1 目标

幺幺零不是钉钉转发器，而是所有工作渠道的消息中间层：

1. 把钉钉、飞书等来源统一成可回放的事件；
2. 在中间层结合会话历史、平台状态和模型分析，形成结构化判断；
3. 按配置分发到通知、任务、执行器和文档；
4. 内核只负责事件、能力、发件箱与审计，渠道、模型、执行器全部插件化；
5. 最终做到：消息进得来、上下文接得上、判断说得清、任务派得出、结果回得来、全过程可回放。

当前阶段先把中间层做扎实，不追求无人值守的自主行动。

### 1.2 当前基线

- `message.received` 已由多来源归一成 `Event` 并落库。
- `scenario-analysis` 已对全部来源做一次中间层分析，产出 `message.analyzed`：
  - 上下文：`state.message.history`，同一 channel 的已存事件，默认最近 20 条；
  - 摘要：`capability-ai` 的 `ai.summarize`，一次性 CLI 调用；
  - 失败：`status=degraded`，分发不丢消息。
- `scenario-dingtalk-feishu-relay` 已改为只消费 `message.analyzed`，卡片含摘要、原文、图片内联。
- 454 单测通过；doctor/docs 通过。

### 1.3 差距

1. **上下文不完整**：早期只能读平台启动后的 `events`；第一轮已加 `state.history.fetch`，DingTalk source 可补拉，其他 source 尚未实现。
2. **分析只有摘要**：没有意图、主题、项目、紧急度、建议动作、置信度；分发仍按 source 过滤，不是按分析结果路由。
3. **旧链路未完全收口**：`classifier-llm` 仍在；`dev-dispatch` 已迁移到 distribution 出口但默认停用；`dsh` headless 缺模型凭据，分析器实际走 `claude`。
4. **可观测不足**：没有一条消息从上下文、分析、路由到发件箱的统一视图；模型耗时、失败率、成本没有指标。
5. **边界未验证**：模型降级、渠道不可用、历史拉取失败、重复投递、模型洪峰还缺系统化验收。

### 1.4 非目标

- 不 fork `dsh-superagent`；不引入常驻 Router / Worker 自主执行。
- 不让模型决定路由、执行器、目录或是否动手；这些仍由配置和代码决定。
- 不提前做 Ticket / Assignment / 多 agent 编排；需要连续任务生命周期时再立项。
- 不把完整聊天记录无限期留存；上下文有窗口和保留策略。

## 2. 技术设计

### 2.1 分层

```text
Source adapter
  → Event（归一化、落 events/event_log）
  → message.received
  → 分析服务（上下文 + 模型能力）
  → message.analyzed（结构化分析）
  → 分发消费者（按配置路由）
  → 通知 / 任务 / 执行器 / 文档
  → outbox / 回执 / 审计
```

内核不出现钉钉/飞书分支；分析服务不出现渠道分支；分发消费者不直接读原始平台载荷。

### 2.2 契约

**`state.history.fetch`（内核读能力，effect=none）**

```ts
input: {
  source: string
  channelId: string
  before?: string
  limit: number
}
output: {
  items: { externalId, actor, text, occurredAt }[]
  complete: boolean
  via: 'event-store' | 'source-history'
}
```

- 内核按 `source` 找可选 `Source.fetchHistory`；找不到/失败退回事件库；
- source 插件只实现自己的历史适配，分析服务不直接调任何平台 CLI；
- 平台事件库始终有兜底实现；
- 各 source 插件可选提供外部历史，缺省退回事件库。

**`message.analyzed` v2**

```ts
{
  event: Event
  analysis: {
    summary: string
    urgency?: 'low' | 'normal' | 'high'
    entities?: string[]
    evidence?: string[]
    status: 'ok' | 'degraded'
    model?: string
    contextCount: number
  }
}
```

`summary` 是分发卡片的展示字段；`urgency/entities/evidence` 是理解层字段，**不携带 intent 判断**——是否派工、归哪个项目、用什么执行器仍由 Intent/规则/配置决定，避免同一消息两条判定链。

**路由配置**

```yaml
distribution:
  rules:
    - when: { intent: bug, confidence: '>=0.7' }
      to: [feishu-card, dispatch]
    - when: { intent: dev-request, project: personal-lingcub }
      to: [feishu-card]
```

规则匹配由代码执行，输入是 Intent（规则/判断器产出），不是模型直接给的 `analysis`；模型只产出 `analysis`，不产出最终路由。

### 2.3 失败与回放

- 历史拉取失败：退回事件库，`via=event-store`，继续分析。
- 模型失败/超时：发 `degraded`，分发仍发原文，卡片不显示 AI 行。
- 分发失败：走 outbox 重试/死信，不丢消息。
- 重复投递：Event id / `message.analyzed` 自然键幂等。
- 每条分析可从 `event_log` 回放；模型版本、提示词版本、上下文条数必须可查。

### 2.4 观测

- 一条消息的追踪键：`eventId`。
- 记录：来源、channel、上下文条数、模型、耗时、状态、摘要、命中路由、outbox receipt。
- UI 后续加“消息详情”：上下文 → 分析 → 路由 → 发件箱。

## 5. 风险与回滚

| 风险 | 处理 |
|---|---|
| 模型调用成本/延迟上升 | 规则先挡、`maxInFlight`、超时/降级、观测成本 |
| 外部历史接口不稳定 | 事件库兜底，source 适配器隔离 |
| 路由配置误发 | 默认 observe / 人工确认；路由变更可回放 |
| 旧链路双跑 | 分批迁移，旧路径先只读/停用再删除 |
| 隐私与留存 | 上下文窗口、保留策略、敏感字段过滤 |

回滚以能力开关和配置为主；不把渠道逻辑写进内核，避免回滚需要改代码。
