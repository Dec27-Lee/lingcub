## 需求描述

把「一个飞书话题 = 一个本机窗口」从只支持 claude 扩展到 claude + dsh，并补齐三件产品能力。用户原话拆解如下。

**R1 从飞书拉起会话（claude / dsh 都行）**

- 在飞书控制台话题群里发起：先选执行器（claude code / dsh），再选工作区（列真实目录 + 历史会话），然后拉起会话。
- 拉起成功即在话题群开一棵话题，与窗口绑定，并自动置顶。

**R2 把本机窗口同步到飞书**

- 电脑上已经打开/正在跑的 claude code 与 dsh 窗口，要能出现在飞书里：一棵话题一个窗口，可看实时状态，可在话题里继续对话。
- 关闭或长时间无更新的窗口，取消置顶（不再占用置顶位）。

**R3 每窗口一张实时状态卡**

- 话题内一张卡，原地更新（不刷屏）：执行器、工作区、在跑/等你/完成/失败、当前工具或思考、最后一句输出、用量。

**R4 机器人私聊只发重点**

- 机器人（飞书，非钉钉那个）私聊只发重点：关键实时信息、等你决策、任务完成总结。多窗口并行时不逐条转播。

**R5 分层约束（用户明确要求）**

- 按 001–005 的分层做：内核只管状态与事件，执行器插件管窗口，频道插件管飞书，场景插件管交互，能力插件管判定；插件之间不互相调用，副作用一律经 outbox。

## 技术设计

### 分层落点（谁做什么）

| 层 | 模块 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| 内核 | `src/kernel/store.ts`、`session-open.ts`、`runtime.ts` | 会话行、发件箱、状态变迁、事件总线；扫描拍只调端口 | 不认飞书/终端/CLI |
| 执行器插件 | `executor-claude-v2`、`executor-dsh-v2` | 起窗口、投文本、读状态、停窗口、枚举本机窗口与工作区/历史会话 | 不碰飞书、不建话题 |
| 频道插件 | `channel-feishu` | 建话题（根消息 + `reply-in-thread`）、发卡/改卡、置顶/取消置顶、私聊发送 | 不判断该不该发 |
| 场景插件 | `scenario-session-console`（重构）、`scenario-session-status`（新）、`scenario-topic-pin`（新）、`scenario-focus-dm`（新） | 交互流、状态卡刷新、置顶对账、重点消息分派 | 不直接调 CLI、不起进程 |
| 能力插件 | `capability-focus`（新） | 规则 + 模型判定「这条值不值得打扰人」 | 不发送、不落库 |

关键不变式（沿用 005 §2）：一棵话题最多绑一个会话；一个执行器会话只被一棵话题绑定；`dead` 会话不再接消息；未绑定话题的消息仍走判断层，不猜。

### 状态来源（实测，明细见 `data/research/window-observability.md`）

| 窗口来源 | 能看到的 | 能做的 | 判据 |
| --- | --- | --- | --- |
| lingcub 拉起（claude terminal） | 预给 uuid；SessionStart/Stop/Notification/PreToolUse 全走钩子；transcript 全量 | 看状态、投递、停止、改卡、置顶 | 全通 |
| lingcub 拉起（claude headless `--bg`） | `--bg` 只回 8 位短 id 入库，钩子给全 uuid → `findSessionByExecutor` 精确等值**必然认不出**，且 warn 用 debug 级（当前 info 不落盘） | 同上（修好 id 归一后） | 有 bug，见下 |
| 用户终端自己开的 claude | `claude agents --json` 实测 5 条 interactive：sessionId/pid/cwd/kind/status/name；`~/.claude/sessions/<pid>.json` 多给 `messagingSocketPath`+`status(busy\|idle)` | 看状态、在话题里发话（命名管道 + peerToken）；停止只提示 | 可枚举、可注入 |
| 用户终端自己开的 dsh | **无列举命令**；只有 `~/.dsh/sessions/<slug>/<id>/session.v4.jsonl.zstd` 文件，判活只能看 mtime | 只读镜像（不投递） | 只能靠文件与 mtime |

三条硬约束：

1. **观测只能采样，不能订阅**：claude 没有「窗口关闭」事件，只能轮询 `claude agents --json` / pid 文件消失；pid 文件会 churn（50664 → 35116 一分钟内换过）。
2. **身份四套写法不可混用**：全 uuid（钩子/agents）、`--bg` 短 id（8 位）、name、dsh session-id。入库必须统一成全 uuid 或一列一义。
3. **写回不对称**：claude 需要活进程 + 每次重读 peerToken + `crossSessionInbound:accept`；dsh 必须会话不在跑 + cwd 一致且**不幂等**（`--session-id` 追一轮就是一轮）。UI 必须区分「可注入 / 仅可见」。

### 取证发现的四处必须先修

1. **thread_id 形态错配（本轮已修）**：飞书话题 id 是 `omt_…`，锚消息 id 是 `om_…`。原实现把锚消息写进 `sessions.thread_id`，`findSessionByThread` 又按等值查 → 话题内消息命中不了会话，被当成新话题反复开窗。已改为 `thread_id` / `root_message_id` 双列匹配（thread 命中优先），写入侧也不再让 `om_` 冒充 thread。
2. **headless 结果永远回不来**：`--bg` 入库的是 8 位短 id，钩子回传全 uuid，`findSessionByExecutor` 精确等值必然落空；命中失败只 `log('debug')`，当前 `log.level=info` → 一行不落盘（今日 grep「未知会话」命中 0）。修法：入库同时记全 uuid 与短 id，反查两列都认，并把这条日志提到 info。
3. **bus 档没有开窗实现**：`control.messages=bus` 让 `pipeline.ingest` 在 502 行短路，开窗/选择/换会话整段失效；`dev-dispatch` 又关着，`preflight` 还明文禁止 bus+open。→ R1 必须在 v2 场景里实现开窗，并同步改 preflight 的这条守卫。
4. **自动置顶从未生效**：`channels.feishu.pinCards` 默认 `false`（config 里连键都没有），v2 侧也没有 pin 生产者。→ 置顶/撤置顶要作为独立场景实现，不能寄望旧配置。

### 判定与出口（实测，明细见 `data/research/priority-notify.md`）

- `Action` 现有 16 种，**没有** `dm.send` / `topic.open` / `status.changed`；`notify.card.send` 的 `chatId` 可以是任意会话（含 p2p），所以私聊缺的是「模板 + 收件人来源」，不是能力。
- 重要性只有 `ai.summarize` 的 urgency 三档自评，无规则表、无评测集；`distribution` 的 `targets` 是出口名不是收件人。
- `session.turn.ended` 实测 0 条；dsh 没有钩子也没有轮次事件 → 「任务完成」目前只有 claude 一条来源，dsh 要靠 headless 进程退出补。
- 现成可复用：`state.workstation.snapshot`（在跑数）、`transcript.currentTurn`（files/tool/openSubtasks）、`buildStatusCard` 字段。

### 交互流（R1）

```text
群内非话题消息
  ├─ 命中会话（chat+thread）→ 直接投给窗口
  ├─ 有待选（choices 未过期）→ 按序号/别名作答
  └─ 否则 → 开窗向导
       ① 选执行器卡：claude code / dsh（本次新增）
       ② 选工作区卡：真实目录（按最近活跃）+「历史会话」页签（dsh 也要列）
       ③ 发起：session.open → 执行器起窗口 → 频道发根消息成话题 → 置顶 → 就绪卡
```

### 置顶对账（R2）

- 新话题开出来 → 置顶；`session.status` 连续 `idle` 超过阈值（默认 30 分钟）或 `dead`/窗口已关 → 取消置顶。
- 只撤自己置的（`cards.pinned_at` 记录），别人的置顶不动；5 分钟内新置的不撤，每轮最多撤 10 条。
- 关闭判定：执行器 `read()` 抛「会话不存在」或进程消失 → 置 `dead` 并撤置顶。

### 私聊重点（R4）

- 触发源只有三类：① 需要你决策（选择题/工具授权/报错等人）② 任务完成（一轮结束且无未完成子任务）③ 关键实时信息（AI 判为高优先级且命中规则）。
- 规则优先、模型只做摘要与措辞（不让模型决定路由）：规则命中 + `capability-focus` 给出一句话总结 → `dm.send`。
- 去重：同会话同类 10 分钟内一条；聚合：多窗口同时完成时合成一条「3 个窗口完成」摘要。

## 后续：置顶缺失（2026-11-09）

**现象**：6 个开着的 claude 窗口，飞书置顶里只有 3 条；其中几个窗口几小时内一直活跃、也没关。

**取证**（本机实测）：`claude agents --json` 报 6 个活会话（c510e321 / f08a0a77 / a1f87681 / 465fe314 / ea88b5b8 / 547db4fc），
`im pins list --as bot` 只有 3 条；日志 05:04–05:20 连续出现「撤掉已停会话 … 的置顶」（ea88b5b8、465fe314、f08a0a77、a1f87681）。

**两个根因**

1. **判据用错**：`reconcilePins` 用「`status==='active'` 且 30 分钟内动过」判窗口还在不在。claude 窗口开着但人在看代码、半小时没发言，就被当成「已停会话」撤置顶，接着又因为同一个判据不为「活」而不补回。claude 的窗口关没关本来有事实来源（`reapDeadSessions` 每轮问 `claude agents --json`），不该再叠时间判据。
2. **本地标记与平台不一致**：`cards.pinned` 是发卡/补 pin 时乐观写的，平台侧被撤（或当初没真的置上）后不会纠正。`isCardPinned` 一直为真 → `pickPinsToRestore` 永远跳过它，那个窗口的置顶就永久缺失（f08a0a77、ea88b5b8 正是这种）。

**改动**

- `windowStillOpen()`：claude 只看 `status`（关窗由 `reapDeadSessions` 标 dead）；dsh 没有进程信号，仍按 `staleMinutes`。
- `reconcilePins`：拿到平台置顶列表后**先校准**本地 `pinned` 标记（平台有→true，没有→false），再算孤儿与补回；补回的条数上限跟活窗口数走（原来写死 3，6 个窗口要等好几轮）。
- `listPins` 加 10 秒节流：它是一次真实接口调用（CLI 子进程），原来跟着每轮 tick 打。

**验证**

- 单测 611 全绿（新增 `windowStillOpen` 五条断言 + 「claude 八小时没发言也不撤置顶」）。
- 变异反证：把 claude 分支改回按时间判 → `windowStillOpen` 与「八小时」两条真红，恢复后绿。
- 真机：重启后日志连续 6 条「补回活窗口 … 的状态卡置顶」（05:27:04–05:27:12），`im pins list` 由 **3 条变 8 条**（6 个 claude 窗口 + 2 个 dsh 会话），与「活窗口 = 一张置顶状态卡」一致。

```

**根因是调用频率，不是判据**：

- `cardRefreshMs` 默认 **2 秒**，六七个 claude 窗口 = 每秒 3 次改卡，每次都起一次 CLI 并重新取 tenant_access_token → token 接口超时。
- 取 token 超时被 `patchCard` 冒泡成「改不动」，代码据此**换新卡**（旧注释写的是「超 14 天/被撤回」这类永久的，但临时错误也走了同一条路）。
- 换卡 = 撤旧卡置顶 + 给新卡重新置顶；而重新置顶又撞在同一个超时上 → 那个窗口最终一张置顶都不剩。

**改动**

- `config/lingcub.yaml`：`sessions.cardRefreshMs: 15000`（原来吃默认 2000）。
- `isTransientCardError()`：网络/超时/限流（`network`、`timeout`、`deadline`、`429/502/503/504`、`ECONNRESET`）判为临时失败，**保留原卡**、由下一轮重试；只有「消息不存在/被撤回」才换新卡。

**验证**：`pnpm test` 612 全绿（新增 `isTransientCardError` 五条断言）；重启后等 3 分钟，`im pins list` 稳定 **7 条**，与库里 7 个 active 会话（6 claude + 1 dsh）逐条对上，`pinnedLocal` 与 `onPlatform` 全部一致；这段时间里仍发生了 4 次「状态卡换新」，但置顶数没有再掉——说明换卡后的重新置顶已经能成功。

### 再来一轮：换卡瞬间会「一条置顶都没有」

**现象**：用户看到「pin 里一个会话都没了」，几分钟后再查又恢复成 7 条。数据库、平台 pin、消息本身都正常（7 条 `+messages-mget` 全部可取到），不是数据脏。

**取证**：平台 pin 的 `create_time` 跨度是 `05:56:40 / 05:57:37 / 05:58:36 / 05:59:12 / 05:59:31`——五条在四分钟内被**连续重 pin**。日志里每轮对话都会 `状态卡换新`，而换卡的实现是：

```
takeCard（删掉旧卡记录） → pinMessage(旧卡, false)（立即撤） → 发新卡 → 给新卡置顶
```

发卡本身要几十秒（实测 `05:44:03 换新` → `05:44:38 才创建`，35 秒）。这段时间里**旧卡已撤、新卡未到**，那个窗口一条置顶都没有；几个窗口同时换轮，用户看到的就是「置顶全空」。

**改动**（顺序反过来：先有新置顶，再撤旧的）

1. 换轮时**不再主动撤旧卡置顶**，只把旧卡消息号记进 `#handoverPins`（等待交接）。
2. `reconcilePins` 的孤儿撤销跳过交接中的旧卡；等到该会话的当前卡 `isCardPinned === true`（新卡置顶成功），才把它移出交接、按普通孤儿撤掉。

代价是最多同时存在「旧卡 + 新卡」两条置顶十几秒；换来的是任何时刻都至少有一条。

**验证**：`pnpm test` 612 全绿；重启后连续采样 12 次（每 5 秒一次，共 1 分钟）：`7 7 7 7 7 7 7 7 7 8`，最小 6（重启瞬间）、最大 8（交接期），**没有再出现 0**；结束时 `im pins list` 7 条，逐条对应活会话，消息均可取。

### 又一轮：话题里冒出「你不是我开的」窗口

**现象**：群里出现 `电脑上开的终端窗口（dsh d9fbed45 / f29d0d4d）` 这类话题，还有 `你是智能协作模式的主助手，`（TongClaw 任务）、`请根据以下用户请求完成任务` 这种。用户：除手动发起的以外，只该有他亲手开的窗口。

**根因**：dsh 侧「在跑」的判据是**会话文件 90 秒内被写过**——dsh 没有进程/窗口概念，只能这么推断。于是**别的项目在 dsh 里跑的 headless 任务**（TongClaw 的 `conv_*` / task 目录）也被当成「用户刚打开的窗口」，每跑一个任务就建一条话题。

**取证**：扫了全部 2500+ 份 dsh 转录头，程序化会话与用户窗口的差别只有一处——

| 来源 | header |
| --- | --- |
| 用户窗口（`session-7ae71de9` / `d9fbed45` / `f29d0d4d`） | `{"type":"session","delegationDepth":0,"agentPreset":"yue"}` |
| TongClaw 任务（`conv_ad6` / `conv_94d` / `orchestr`） | `{"type":"session","delegationDepth":0}` ← 没有 `agentPreset` |

统计：`agentPreset` 为「无」的 2257 份（子代理 + 程序化任务），有值的（`yue` 56 / `liangshen` 80 / `standard` 37 / `liangshen-teams` 46）才是人开的。

**改动**（`isUserWindowHeader` 加两道，任一不满足都不采纳）

1. **必须有 `agentPreset`**：人开的会话一定选过 agent；headless 任务没有。
2. **`createdAt` 必须在 10 分钟内**（`sessions.adoptNewMinutes`）：把半年前的会话翻开写一行，mtime 会刷新，但创建时间不会。

**清理**：4 个误采纳会话（`conv_stu` / `conv_ad6` / `conv_94d` / `orchestr`）标 dead；置顶由对账自动撤（`windowStillOpen` 看 status）。话题消息不删，只停止维护。

**验证**：`pnpm test` 613 全绿；`pnpm test:check` 登记完整（新增 `FLOW-INT-011`）；变异反证——去掉创建时间那道闸，`FLOW-INT-011` 真红；去掉 `agentPreset` 判定，「session 头判定」真红。重启后日志不再出现新的「接进飞书」记录。

### 再一轮：dsh 那个窗口的置顶每半小时掉一次

**现象**：用户又说「pin 里的话题又没了」。实测：5 个 claude 窗口的置顶都在，唯独 **dsh（本会话）** 那条掉了。

**根因**：dsh 没有进程状态，`reapDeadSessions` 按「30 分钟没动静」把它降成 `idle` → 置顶被撤；再下一轮 `adoptLocalWindows` 扫到它还在动 → 复活成 `active` → 置顶补回。如此循环。

而「动静」原来只在**用户发消息/钩子回执**时刷新，人在窗口里跑工具、只是没说话，就一直是「没动静」。

**改动**：`adoptLocalWindows` 扫到已知且 active 的 dsh 会话时 `touchSession` —— dsh 的 `listLiveSessions` 本来就是「会话文件 90 秒内动过」，能扫到就说明它真的在动，这就是最直接的活跃证据。

**验证**：`pnpm test` 614 全绿（新增 `FLOW-INT-012`）；采样 1 分钟：`6 6 6 7 8 8 7 6 6 6` —— 波浪是换轮交接（旧卡+新卡并存十几秒），**底数 6 = 5 个 claude 窗口 + 本 dsh 会话，没有掉到 0，也没有再出现「只有一半」**。

### 定案：状态卡只留一条，而且必须在话题根上

**现象**：用户截图「Pin 消息」面板里只有 2 条，而 `im pins list` 返回 6 条。他说「在群里看不到，或者会自动消失」。

**取证**（`+messages-mget` 看 `message_app_link` 里的 `thread_position`）：

| pin 的卡 | 位置 |
| --- | --- |
| 5 条（一轮一张换出来的状态卡） | 话题内，`thread_position=20/36/48/61/77` |
| 1 条（adopt 时生成的根卡） | **主消息流**（没有 position） |

**结论**：飞书话题群的「Pin 消息」面板在群主消息流里**只列主消息流的消息**。话题内第 N 条被 pin 了，API 查得到、面板里没有——这正是「pin 里看不到」的全部原因，和数据库、置顶标记都无关。

**改动**（两个语义收回）

1. **同一个窗口永远只用一条消息**：删掉「新一轮 → 换一张卡」的逻辑，改为原地 patch 话题根。理由：根是唯一在主消息流可见的那条；换卡就等于把窗口从置顶面板里摘出去。
2. **`card_upsert` 一律打在 `rootMessageId` 上**：历史遗留的「卡记录指向话题内消息」由 `reconcilePins` 迁回根（`状态卡迁回话题根`），pin 随之落到根。
3. 根改不动（超 14 天 / 被撤回）**不再换卡**：换根等于换话题锚点，整个窗口失联。改为报错重试。

代价：话题里不再有「上一轮结束」的灰卡，历史轮的明细靠话题内的回复消息回溯。这是为「置顶面板 = 窗口列表」让路。

**验证**：`pnpm test` 614 全绿（改写 2 条旧语义用例：`话题根改不动也不换消息`、`状态卡不换消息：…原地更新`）；重启后 `im pins list` 6 条**全部 `thread_position` 为空（主消息流根）**，6/6 可见。

### 全链路审计：四次「置顶/卡片反复出问题」其实是同一类缺陷

**触发**：用户要求「对整个链路做一次架构检查和代码检查，就这些问题反反复复」。

**做法**：四路并行只读审查（钩子链路 / 飞书频道与卡片 / 执行器与窗口发现 / store 与状态一致性），
判据取 `docs/design/*.md` 与 `docs/runtime/sessions-and-windows.md` 的可判定条款，主线另审 `pipeline` 的卡片与置顶生命周期。

**根因归类**（反复出问题的都不是「某个分支写错」，而是四类结构性缺陷，每类都在多处复发）

| # | 缺陷 | 本任务里的表现 |
| --- | --- | --- |
| R1 | 同一事实多处存、各自漂移，没有唯一真相与校准 | 卡在哪条消息两处存（`cards.message_id` / `sessions.root_message_id`）；置顶没置顶三处判（本地 `pinned` / 平台 pins / `sendCard` 内部顺手钉）；「这轮刷过没」(`card_turns`) 只增不删 |
| R2 | 判定散落，且拿推断当事实 | 「窗口还开着吗」四处各一套（`windowStillOpen` / 关窗回收 / 采纳 / `listLiveSessions`）；dsh 把「文件 90 秒没动」当关窗信号 |
| R3 | 失败静默降级成「看起来成功」 | 发卡没解析到消息 id 仍返回成功；CC Switch 配置读坏当空对象写回；超时被判成永久失败 |
| R4 | 状态机缺失 | 一轮结束既不记「已回复」也不清「画过哪轮」；`dead → active` 复活不清旧轮次 → 状态卡永不重建 |

**最要命的一条**（R4 + 一次多余的副作用）：`Stop` 钩子每轮结束都入队 `card_retire` —— 把状态卡改成灰卡、
**撤掉置顶**、删掉卡片记录。于是「一轮结束 → 置顶没了 → 下一轮 patch 回来但不补钉 → 等 10 秒对账补」。
日志计数：`状态卡已收掉` **117 次** vs `补回活窗口置顶` **21 次** —— 大部分收掉之后根本没补回来。
这就是「pin 会自动消失」的直接原因；上一轮的「根迁移」只解决了「话题内不可见」，没动这条。

**改动**

1. **删掉收卡动作**（`Action.card_retire` 及其各处入队）：一轮结束只把卡改内容（显示「已结束」），置顶一直留着。
   `Stop` 改为 `clearCardTurn` + `markReplied`，下一拍原地重画，兜底不再重复补发。
2. **置顶统一由内核做**：`createDeliver.ensureCardPinned` —— 建卡/改卡之后都校验一次，缺了就补；
   频道不再自己顺手钉（它 pin 失败只 warn，内核却记成成功，两边对不上）。本地记着已钉就跳过（一次 pin 一个子进程）。
3. **存活只看 `status`**：`windowStillOpen(s)` 去掉时间判据；关窗回收只处理 claude（有 `agents --json` 进程事实），
   dsh 不再按「没动静」降级——它没有关窗信号，只由 `#停止` 结束。
4. **复活要清旧轮次**：`setSessionStatus(…, 'active')` 时删 `card_turns`，否则状态卡永远停在上一轮。
5. **签名抹平 m:ss**：`normalizeCardLine` 原来只认「X 分 Y 秒」，前两分钟显示的是 `0:07`，一秒一个新签名。
6. **临时失败判据认中文**：`spawn` 抛的是「命令超时」，原来只认英文关键词。
7. **静默失败改明确失败**：发卡没拿到消息 id 直接失败重试；装钩子时原样保留别家钩子的 `timeout` 等字段；
   CC Switch 通用配置 JSON 解析失败就拒绝覆盖；钩子结果去重键改为内容哈希（原来含 `Date.now()`，超时重试会重发）。
8. **`#恢复` 不再把活窗口当可恢复**：注册表里 `status=shell` 的窗口原本被当成已退出。

**验证**

| 项 | 结果 |
| --- | --- |
| `pnpm build` | 干净 |
| `pnpm test` | **618 pass / 0 fail**（改写 6 条旧语义用例，新增 4 条） |
| `pnpm test:check` | 登记完整：120 条 / 118 个用例文件 |
| `pnpm docs:check` | ✔ 链接可达、台账合规 |
| `node scripts/audit-parity.mjs` | 30 功能 + 15 约定，**缺失 0 条**（C8/C9 落点按新语义改写） |

变异反证（4 条新规则逐条做红）：去掉 patch 后的 `ensureCardPinned` → 「置顶丢了要补回来」红；
去掉 `active` 时的 `clearCardTurn` → 「复活要清旧轮次」红；去掉 m:ss 抹平 → 签名用例红；去掉中文「超时」→ 超时判据用例红。四条都已复原。

**线上实测**（重启后）

```

```

**已知未修（记在这里，别当成新问题再查一遍）**

- store：`root_message_id` 无唯一约束、`findSessionByThread` 跨两列 OR 无索引；`listSessions()` 全表扫，`reconcilePins` 一拍调 5 次（`store.ts:findSessionByThread` / `reconcilePins`）。

### 再一轮：dsh 的卡从来没动过，以及钩子在别的目录里全失效

**现象**：用户报「话题中的会话执行过程的实时状态卡片又不显示了」。

**一、dsh 窗口的状态卡是死的（挂了 8 小时）**

库里 5 个 active 会话的卡时间：3 个 claude 在 15 秒内刷新过，`7ae71de9`（dsh）的卡停在 **03:20:52**，8 小时没动。

**根因**：`#refreshOneCard` 里 `transcript = findTranscript(sessionId)` 找的是 claude 的
`~/.claude/projects/*/<sid>.jsonl`；dsh 的转录在 `~/.dsh/sessions/<slug>/<sid>/` 且是 zstd 多帧，
`read()` 也返回空 —— 于是 `if (!transcript && !lastLine) return 0` 每拍都提前退，
卡永远停在「接入那一刻」。dsh 窗口因此从来没有过实时状态。

**改法**：dsh 走 `#refreshFactsCard` —— 用库里已有的事实画卡（最后一句 `last_text`、
最后活跃 `last_active_at`、上一轮结束 `last_stop_at`）。「在跑」三条同时成立：`status=active`、
最近 2 分钟有活动、那次活动晚于上一轮结束。活动时间来自 `adoptLocalWindows` 每 20 秒的扫描，
所以它反映「窗口有没有在写东西」，不是「用户多久没说话」。claude 分支保持不变
（读不到转录说明这一拍异常，不能拿事实卡去覆盖正常进度卡）。

实测（重启后）：`状态卡已更新：sess-local-7ae71de9` 出现；平台上的卡内容为
`🟢 在跑（最近活跃 12 秒）` + `📁 E:\Develop_E\lingcub` + 一句说明「没有可读转录，只反映窗口是否在动」。

**二、钩子在窗口自己的目录里全部失效（这才是「钩子没到」的真因）**

`data/hook-errors.log` 里写着 `端点信息缺失（没有 data/hooks.json）`。查 active 窗口的 workspace：
**4 个 claude 窗口全在 `E:\Develop_E\tt\tt-design-space-ai`**，不在 lingcub 目录下。

**根因**：`main.ts` 的 `const ROOT = process.cwd()`。钩子是 claude 在**窗口自己的 cwd** 里执行的，
于是 `readHookInfo(ROOT)` 找的是 `<那个目录>/data/hooks.json` —— 不存在 → 钩子「静默成功」退出 0，
Stop / Notification / AskUserQuestion / PermissionRequest / SessionStart **五条钩子全部失效**。

这解释了此前所有相关症状：日志里 221 次「钩子没到，补发这一轮的回复」、日志里一条「结果已入队」都没有、
问答卡片点了没反应、状态卡停在「在跑」。

**改法**：`ROOT` 从**入口脚本位置**推（`resolve(dirname(process.argv[1]), '..')`），不再用 cwd。
钩子命令本来就是绝对路径，所以不用重装钩子，也不用重启那些 claude 窗口。

**验证**（把 cwd 设成 `E:\Develop_E\tt` 手动跑钩子，等价于窗口内触发）：
修复前打印「端点信息缺失」；修复后同一命令在日志里留下
`钩子：未知会话 probe-from-tt-0001（不是本进程起的），忽略` —— 说明端点可达、root 正确，
只是这个探针 id 不在库里（预期）。

### 再一轮：上下文进度条的分母是猜的，整条画错一倍（2026-11-10）

**现象**：完成通知卡上写着 `📦 ████ 100% 245k · Tokens 32.3M`，而同一个窗口的终端状态栏是
`49% (245k/500k)`。进度条满格、百分比翻倍。

**根因**：分母是配置里的常量。`statsLine(file, contextWindow)` 四处调用点都写成
`contextWindow ?? 200_000`，而 `config.contextWindow` 的默认值正是 200000 ——
245k / 200k = 122%，`contextBar` 再 clamp 到 1，于是「满格 100%」。
真实窗口是 500k，**转录里根本没有窗口大小**，200k 从来只是猜的初值。

**窗口的真值在哪**（本机实测）：`~/.claude/settings.json` 的 `env` 段——

```
CLAUDE_CODE_AUTO_COMPACT_WINDOW=500000   # 自动压缩触发线，终端状态栏的分母就是它

不能按模型名推断：服务商由 CC Switch 切换并**整体覆盖**这份 `settings.json`，
同名模型（`deepseek-v4.1-flash`）挂不同 provider 时窗口并不一样。

**改动**

- 新增 `src/kernel/context-window.ts`：`resolveContextWindow(fallback)` 按
  「本进程 env → `settings.json` 的 env → 配置兜底」三级取值；读文件按 mtime 缓存。
  钩子进程是 claude 拉起的子进程，`process.env` 里直接就有真值，那一条优先。
- 四处调用点改用它：完成通知（`hook-handlers.ts` 两处）、状态卡（`card-content.ts`）、
  兜底补发（`pipeline.ts`）。
- `config.contextWindow` 默认值改 **0 = 不知道**：给不出分母就只写 `245k`，不画百分比。
  宁可少一行，也不拿猜的值画一个的进度条。
- 平台事实写进 `docs/platform/contracts.md`（claude 段）。

**验证**

| `pnpm build` | 干净 |

变异反证（三条，都已复原）：关掉 settings.json 分支 → 「分母取 claude 声明的窗口」红；
忽略进程 env → 「钩子进程继承的 env 优先」红；把配置兜底的 0 也当分母 → 「拿不到分母不画百分比」红。

### 再一轮：dsh 的卡其实在 pin 里，是内容冻住了（2026-11-10）

**现象**：用户问「这个任务窗口为什么没在 pin 里看到」。

**先排除置顶问题**（实测）：`im pins list --chat-id oc_20fef3…` 返回 5 条，其中就有本窗那张
`om_x100b60278fd0ccb4dd1fd5a597fea6c`（`thread_position` 为空 = 主消息流，面板应可见），
库里 `cards.pinned=1`、`card == root_message_id`，5 个 active 会话逐条对上。置顶没丢。

**真问题**：这张卡的内容冻在 8 小时前——

```
卡内容（实测）  <card title="幺幺零项目架构开发 · 已完成">⚪ 空闲（最后活跃 12 小时 0 分）
cards.updated_at 2026-11-09T23:42:51Z        ← 8 小时没动
日志「状态卡已更新：sess-local-7ae71de9」最后一条也是 23:42
```

**根因是两道闸叠在一起**（开 debug 日志抓到的，命令与结论都在下）：

1. `#refreshFactsCard` 每拍都在跑、算得也对（`DEBUG dsh 状态卡：sess-local-7ae71de9 → 在跑`），
   但它画的是 `🟢 在跑（最近活跃 12 秒）`；
2. `normalizeCardLine` 有一条 `.replace(/\d+\s*秒/g, '')` —— 「12 秒」「45 秒」抹完是**同一个字符串**，
   dsh 事实卡只有 4 行、只有这一处会随时间变，抹平后**签名恒定**；
3. 入队判重键是 `${sessionId}-${signature}`，签名恒定 → 第一条 done 记录永久命中 → 之后再也不入队。

claude 的卡没有暴露这条，是因为它的内容里有工具名、文件数、正文，签名本来就会变。

**改法**

- 事实卡的「最近活跃」改用分钟粒度 `formatAgo`（`刚刚` / `N 分钟前` / `N 小时前`），
  并把它从括号里挪到 `·` 后面：`🟢 在跑 · 最近活跃 刚刚`。
  1 分钟内显示「刚刚」恒定是对的；过了一分钟文案变 → 签名变 → 自然会 patch。
- `card-content.ts` 里 `formatAgo` 本来就有（注释写着「空闲计时只到分钟，粒度直接决定发多少次请求」），
  是事实卡没用它。

**验证**

```
2026-11-10T08:06:51Z INFO 状态卡已更新：sess-local-7ae71de9
卡内容：<card title="幺幺零项目架构开发 · 进行中">
        🟢 在跑 · 最近活跃 刚刚
        📁 `E:\Develop_E\lingcub`
```

- `pnpm test` **632 pass / 0 fail**（新增 1 条）
- 新增用例把机理写进断言：`normalizeCardLine('…12 秒') === normalizeCardLine('…45 秒')` 必须相等
  （这就是冻卡的成因），而 `…1 分钟前` 与 `…2 分钟前` 必须不等（这就是修复生效的条件）
- 变异反证：把事实卡换回 `formatElapsed`（秒级文案）→ 原 dsh 用例里
  「不能写秒」那条真红，已复原
- 中途临时把 `log.level` 调成 `debug` 取证，已改回 `info`（配置无残留 diff）

**已知代价**：窗口刚活动完的 1 分钟内，卡上显示「刚刚」且不会重画；超过 1 分钟按分钟重画一次，
超过 1 小时按小时。这与 `cardRefreshMs=15000` 的节流一致，不会把接口打满。

### 再一轮：dsh 窗口从来不会回消息（2026-11-10）

**现象**：用户说「pin 里能看到当前会话了，但没看到你发送的消息」。

**取证**：那个话题里总共 5 条消息，最后一条是 2026-11-09 11:51 的问答卡；`events` 表里也没有该话题的消息。
库里这个会话的 `replies`、`session_turns` 都是空的。**一条都没发过，不是发丢了。**

**根因**：claude 窗口的结果靠 Stop 钩子回传，dsh 没有钩子 —— 它只能「只进不出」：
飞书话题发消息能投进窗口（`scenario-session-post`），但窗口跑完没有任何信号回到飞书。

**dsh 的转录能不能读**（这是能不能补上的关键，实测）：

| 尝试 | 结果 |
| --- | --- |
| `zstdDecompressSync(整份文件)` | 只解出**第一帧**（1 行 session 头），31 MB 的其余部分丢掉 |
| 流式 `createZstdDecompress` | 解完第一帧就报 `Unknown frame descriptor` |
| **按帧魔数 `28 B5 2F FD` 切开逐帧解** | ✅ 尾部 4 MB = 3419 帧 / 6070 条记录；真实文件尾部 2–4 MB → **2974 条记录 / 226 ms** |

dsh 把会话写成**多帧拼接**的 zstd（一帧一段 JSONL，追加写入），Node 的原生解压器只认单帧。

**事件里有什么**（真实分布，尾部 6070 条）：

```
1004 tool/result   1002 tool/call   919 step/start / step/end   919 assistant/message
 514 job/registered  513 job/settled  122 user/message   23 turn/start / turn/end
```

→ `turn/end` 就是「这一轮跑完了」，正文在同 turn 的 `assistant/message`
（`data.message.content[]` 里 `type === 'text'` 的块；`reasoning` 是思考过程，不能发出去）。

**改动**

- 新增 `src/kernel/dsh-transcript.ts`：
  `splitZstdFrames`（按魔数切）、`contentText`（只取 text 块）、`lastFinishedTurn`（取最后一个 `turn/end` 那一轮）、
  `readDshRecords`（只读文件尾部，尾部找不到 `turn/end` 就把窗口翻倍）、`findDshTranscript`、`lastDshTurn`（按 mtime 缓存）。
- `adoptLocalWindows` 每 20 秒扫到活着的 dsh 窗口时，顺带检查它转录里有没有新的一轮结束 →
  按 claude 通知卡的同一套格式发回话题；判重记 `last_replied_turn = turn/end 的 seq`，重启也不重发。

**实测**

```
2026-11-10T08:19:30Z INFO dsh 结果回传：sess-local-7ae71de9（第 46206 轮）
话题 replies：5 → 6
新卡：<card title="幺幺零项目架构开发">📁 E:\Develop_E\lingcub / 🕐 16:09:05 / --- / 先说结论：…
```

补发的正是上一轮的回复（那一轮结束时这条通道还不存在）。

**验证**：`pnpm test` **638 pass / 0 fail**（+6）；`pnpm test:check` 123 条场景 / 121 个用例文件。
新增用例覆盖：多帧切分、正文只取 text、末轮未结束不算、只有 reasoning 不发、文件不存在不抛错。
夹具用 `zstdCompressSync` 逐帧写一个真的多帧文件，不 mock 解压。

**已知边界**

- 卡上没有「💬 你在终端说」那行：这一轮的 `user/message` 取到的正文是空（结构差异，待查）。
- 每 20 秒对「文件刚变过」的会话解一次尾部，实测 226 ms；文件没变走 mtime 缓存，不重复解。
- 一轮很长（尾部窗口内没有 `turn/end`）时会翻倍重读，上限 32 MB，超了就这拍不发、下一拍再说。

### 再一轮：接入窗口的三个连环坑（2026-11-10）

**现象**：用户报「我终端运行中的窗口，实时状态信息又不推送到飞书了」，并质问为什么反反复复。

**共同点**：出问题的 `s-attach-c510e321` 是**接入的本地窗口**这条支路上的唯一活跃会话。
库里 108 个 claude 会话里只有它一个 `session_id` 是 8 位短 id，其余 107 个是完整 uuid。
新开的窗口完整 uuid + 新 schema 卡 + 小转录，三个坑一个都碰不到；接入的窗口全踩。

**坑 1：短 id 找不到转录（已修）**

`claude agents --json` 只给 8 位短 id，而转录文件名是完整 uuid（`c510e321-4f0a-….jsonl`）。
`findTranscript` 精确匹配 `<id>.jsonl` → 永远找不到 → `#refreshOneCard` 对 claude 直接 `return 0` → 卡永不更新。
修：找不到再按 `<短 id>-` 前缀匹配一次。真机验证：重启后立刻 `会话改名：s-attach-c510e321 → 会话性能优化`
（以前一直卡在「用户第一句话当标题」），`钩子没到，补发这一轮的回复` 也随之生效。

**坑 2：能读到转录了，但那份转录 190 MB（已修）**

`lastUserInput` / `transcriptTitle` / `tailLines` / `scanTranscriptStats` 都是 `readFileSync(整份)` 再切，
每 15 秒读一次 190 MB。全部改成只读尾部；超大文件的累计 tokens 标成 `≥12.3M`，不伪装成全量。

**坑 3：话题根是老 schema 的卡，飞书永远不让改（已修）**

```
code 230099 / ext 200830：schemaV2 card can not change schemaV1
```

那张根卡是 2026-10-30 建的，比 lingcub 接入还早。重试多久都没用，只能在同一话题里换一张新卡，
并在 `cards.detached` 里记住「这张卡不在根上」，让 `reconcilePins` 的「迁回话题根」跳过它
——否则换一张、下一拍又被迁回去，无限拉锯。

**坑 3.5：`detached` 列在线上库长不出来**

把 `ALTER TABLE` 塞进已执行过的迁移里 → 不跑；插进数组中间 → `user_version` 已越过那个下标，也不跑。
最后发现项目里**早就有解药**：`migrate()` 末尾的 `ensureColumns(db)` + `REQUIRED_COLUMNS`
（2026-11-03 踩过同一个坑后加的兜底：版本号只管顺序，保不了某次改表真的生效）。
把 `cards.detached` 加进这张表，老库每次打开幂等补齐。

**真机验证**

```
09:03:16 WARN 状态卡是老 schema（改不动），已换新卡：s-attach-c510e321 → om_x100b601993f69850c13b28eda86283c
09:03:29 INFO 置顶对账：补回活窗口 s-attach-c510e321 的状态卡置顶
（之后无「迁回话题根」，cards.detached = 1）
```

`pnpm test` **641 pass / 0 fail**；变异反证三条（前缀匹配、尾部读、老卡分支）全部真红后复原。

**代价**：那张新卡在话题内，不在群主消息流——「Pin 消息」面板里看不到这一行。
换来的是内容能持续更新。这是老 schema 根卡下唯一可行的取舍。

### 再一轮：卡上的「刚刚」停了 20 小时（2026-11-11）

**现象**：用户第二次报「实时状态又不推送了」。

**取证**：`sess-local-f08a0a77` 的转录**今天 08:51 还在写**（128 MB），`claude agents --json` 里它是 `idle`、
进程还活着；但它的状态卡停在 **11-10 12:22**，内容是 `⚪ 本轮结束 · 刚刚`。
日志里它最后一条也是 12:22:48。同批 `c10bb756`/`625d97e6` 的卡每分钟都在更新——只有它不动。

**根因**：`#refreshOneCard` 里这一句

```ts
if (store.cardTurn(s.id) === openTurn.userId) return 0   // 这一轮已经画过了，不重算
```

本意是省 CPU（同一轮每拍重算没意义），但卡上写的是**相对时间**（`本轮结束 · 刚刚`、`已 3 分`）。
跳过重画 → 「刚刚」就永久停在那一刻。20 小时后那张卡还在说「刚刚」。

这与上一轮修的 dsh 事实卡冻住是**同一类病的两种形态**：
- dsh 那次：秒级文案被签名抹平 → 入队判重永久命中
- 这次：同一轮直接跳过 → 连算都不算

两次的共同假设都是「内容没变就不用重画」，而卡片内容里包含时间。

**改法**

新增 `#cardDrawnAt`（**真正画完**的时间，与 `#cardRefreshedAt` 的节流用途分开）：
同一轮也每分钟放行一次重算——正好对上卡片的分钟粒度。放行后若签名真的没变，投递层仍会跳过，不会白发请求。

顺手给三个静默 `return 0` 加了 debug 日志（没有 sessionId / 工作区或执行器没解析出来 / 读不到转录），
这次就是靠它们确认 dsh 走的是事实卡分支、而 claude 是被上面那句挡住的。

**验证**

```
2026-11-11T01:04:26 INFO 状态卡已更新：sess-local-f08a0a77
卡内容：⚪ 本轮结束 · 12 小时前        ← 修之前是「刚刚」，停在 11-10 12:22
```

`pnpm test` **641 pass / 0 fail**。取证期间临时把 `log.level` 调到 debug，已改回 info。

**遗留观察**：`c510e321`/`aa09bcc8`/`f08a0a77` 三个窗口的 `last_active_at` 停在 11-10 中午。
它们的转录仍在被写（`f08a0a77` 08:51），说明**钩子路径不更新 `last_active_at`**
（只有 `adoptLocalWindows` 对 dsh 才 `touchSession`）。卡上的「本轮结束 · N 小时前」来自转录，是对的；
但库里的活跃时间会偏旧，将来若按它判「窗口还开着」会误判。
