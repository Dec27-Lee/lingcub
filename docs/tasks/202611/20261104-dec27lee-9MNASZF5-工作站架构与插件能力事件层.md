## 结论摘要

1. **现状不是「工作站」，是「一个飞书工作台」**：内核里已经长出一整个业务场景（话题开窗、状态卡、选择题、工具授权、自动回复、置顶对账），而插件只有 `source/classifier/executor/channel` 四个**流程阶段**端口。用户要的三类工作——钉钉消息派工并对反馈人回执、飞书文档待办认领与回写、飞书远程控制 claude/dsh 双执行器会话——每加一条都要改内核。
2. **根因是三处断层**：插件没有「能力面」（拿不到起会话、发消息、写文档），也没有「事件面」（入站只有一个 `emit` 回调）；场景不是插件，只能写进 `kernel/pipeline.ts`。`docs/002` 明说 `ctx.bus`/`ctx.outbox`/`ctx.store` 尚未实现（[002:50](../../002-plugin-contract.md)）。
3. **目标**：内核只留六件事——落事件、投事件、提交副作用、写发件箱、过策略闸、留审计；渠道接入与业务场景都是插件。场景通过「订阅事件 + 提交能力」完成业务，不再由内核按固定顺序驱动。
4. **本轮做了 6 份隔离调研 + 对抗评审**，据此改了四处关键设计：副作用能力一律「提交 + 收据」（不靠订阅者自己幂等）、事件日志只有一份（`event_log`，`events` 降为消息明细）、订阅者不得长等待、新表走幂等 `ensureTables` 不推 `user_version`（否则回滚起不来）。评审的 10 条已逐条处置，见第六节。
5. **执行顺序定为**：P0 设计 → P1 内核骨架 → P2 能力化与投递幂等 → **P4a 钉钉派工垂直切片**（先验证新契约能承载真实需求）→ P3 控制台迁出内核（先立行为金标）→ P4b 分析推送 → P4c 飞书待办 → P4d dsh 会话桥 → P5 工作站视图。控制台搬迁风险最高，放在切片验证之后。
6. **基线（实测）**：`pnpm build` exit=0；`node --test` 255 pass / 0 fail；`node scripts/check-docs.mjs` 通过；库 `PRAGMA user_version=12`；当前有常驻实例在跑（mode=auto，pid 48744），本轮不动它的运行面。

## 一、需求：三条链路与四条分层要求

### 1.1 三条产品链路

| 编号 | 链路 | 现状 | 缺口 |
| --- | --- | --- | --- |
| S1 | 钉钉群／私聊消息 → 分析出需要开发或优化的内容 → 起 claude / dsh 会话开发；完成后对**反馈人**回一条钉钉消息 | `source-dingtalk` 插件存在但字段未实测；判断与派工塞在 `Pipeline.ingest` 的通用分支里 | 无「场景插件」可声明「钉钉消息怎么分析、挑哪个执行器、prompt 怎么拼」；执行器由 `projects.yaml` 静态决定；无钉钉回执能力 |
| S2 | 飞书文档里持续更新的待办 → AI 认领 → 分析后合并或拆分 → 起会话 → 更新文档进度与状态 | `Action.update_doc` / `create_todo` 只有类型，投递时直接抛错（[pipeline.ts:299](../../../src/kernel/pipeline.ts#L299)）；无文档来源、无待办实体 | 需要文档变更事件源 + 待办解析/认领/合并拆分 + 回写能力 + 工作项生命周期；飞书文档/待办接口**尚无实测**（S2 前置） |
| S3 | 飞书消息 ↔ 开发窗口：远程拉起、持续投递、结果通知、手机答题/授权；执行器可选 claude 或 dsh | claude 侧已实现（管道 + hooks）；dsh 侧只有协议结论 | 会话能力埋在 `Pipeline`/`runtime`，不是可复用能力；无「一个平台一个渠道插件」的归属 |
| S4 | 只分析群消息／私聊 → 汇总推回飞书，不起会话 | 无（判断结果只有 `dispatch_session` 与 `reply_only` 两种落地） | 缺按时间窗聚合多源事件的场景 |
| S5 | 更新文档（写回进度、改状态） | 无 | 缺 `doc.write` / `task.update` 能力 |

### 1.2 渠道职责边界（负责人口径）

| 渠道 | 入站 | 出站 | 承接人机任务管理 |
| --- | --- | --- | --- |
| 飞书 | IM 消息、卡片回调、文档变更 | 消息、卡片、文档与待办回写 | **是**：唯一控制台（命令、选工作区、答题、授权、状态卡） |
| 钉钉 | 群／私聊消息（通用） | **只做对反馈人的回执**（`transport.dingtalk.send`）；不做卡片、命令、选择、状态查询 | 否 |
| 其他渠道 | 按插件实现 | 按需提供传输能力 | 否，除非显式实现 |

这条边界决定两件事：钉钉场景的产出必须能「脱离控制台」独立收尾（起会话 → 完成后回执）；飞书的控制台能力（卡片/话题/选择题）只由 `scenario-session-console` 使用，不能被通用派工场景依赖。

### 1.3 四条分层要求（负责人原话归纳）

- **R1 插件层**：渠道接入（钉钉、飞书 IM、飞书文档变更）与功能场景（拉起会话、分析推送、更新文档）都是独立插件，插拔后不影响平台流程。去掉飞书只丢移动端入口，钉钉消息仍能触发流程。
- **R2 内核-能力**：能力开放给插件调用，例如「拉起会话」。
- **R3 内核-事件**：事件发生后插件能订阅、能消费。
- **R4 参考系**：Super-agent 的 Router/Worker 与事件过滤；DSH 自身的 Cordis 插件化（服务 + 事件 + 依赖注入 + 生命周期）。

## 三、架构问题

按严重度排序；每条都是「加需求时会撞上」的结构问题，不是代码风格问题。

| # | 问题 | 为什么是问题 | 严重度 |
| --- | --- | --- | --- |
| A1 | 插件模型是「流程阶段」不是「扩展点」 | 新场景没有位置：加「待办认领」只能在四类里硬塞，或改 `Pipeline`。加一类插件要同时改 `ports/registry/wiring/config` 四处 | 阻断 R1 |
| A2 | 场景写在内核里 | `Pipeline` 是一个场景的全部实现，不是编排。新增 S1/S2 会与现有 S3 逻辑缠绕，`observe` 升档与回放判据也会被稀释 | 阻断 R1 |
| A3 | 没有能力面 | 插件拿不到「起会话/发消息/写文档」，只能被动被内核调用。任何新场景要副作用就得重写内核那段 | 阻断 R2 |
| A4 | 没有事件面 | 入站单回调、结果回传绕开插件直进 `runtime`。插件无法「接入事件后订阅到通知」，也无法在结果出来后追加动作 | 阻断 R3 |
| A5 | 领域模型只有「一条消息 → 一次派工」 | 无工作项（多事件聚合、合并/拆分、进度、工件引用），无待办/文档实体。S2 无法表达 | 阻断 S2 |
| A6 | 平台适配没有单一归属 | 飞书散在三处、内核还拼平台卡片 JSON；「拔掉飞书」会留下内核里的平台知识 | 阻断 R1 |
| A7 | 配置与装配硬编码四段 | 新增插件类别要改 `config-schema`、`wiring`、`doctor`；「配置即事实」退化成「四类配置即事实」 | 中 |
| A8 | 观测面只有配置页 | 桌面面板只看配置与运行态，没有工作项台账、事件流、能力审计；出问题时无法回答「这条消息为什么没派」 | 中 |
| A9 | 发件箱的「至少一次」没有幂等收口 | 崩溃窗口会把已执行的副作用再投一次；claude `--bg` 不认预置会话 id、飞书无幂等键，重投必起第二个会话/重复发消息 | 阻断原则 4 |
| A10 | 三档模式与门禁散在流程里 | `observe` 在 `resolve` 前短路、`suggest` 在 pipeline、`auto` 置信度在 resolve、`allowRoots` 在入队前；没有统一闸口，新场景可以绕过 | 高 |

**不是问题的部分（保留，不推倒）**：`store` 的幂等事件与 `outbox` 去重/重试/死信、`allowRoots` 双保险、三档模式、规则表、回放脚本、30 条能力对齐审计，都是新架构的资产。

## 四、目标架构

### 4.1 分层

```

│ channel-feishu（收 IM/卡片 + 发消息/卡片 + 文档读写）              │
│ channel-dingtalk（收群/私聊 + 对反馈人回执）                        │

┌───────────────▼────────────────────────────────────────────────────┐
│ 内核-事件：event_log（唯一事件史）+ subscriptions + deliveries       │
```

内核不认识飞书、钉钉、claude、dsh、卡片、话题。删掉 `channel-feishu` 目录，钉钉来源与派工链路照常跑。

### 4.2 插件清单 v2

```ts
// 清单声明：提供什么能力、必需什么、可选什么、订阅什么；实现由 setup 注册
export const manifest = {
  v: 2 as const,
  id: 'scenario-dev-dispatch',
  roles: ['scenario'],                         // 元数据，仅用于 doctor/配置页分组
  provides: [{ name: 'dev-dispatch.plan', effect: 'none' }],
  needs: ['session.start'],                    // 缺一个就启动失败
  wants: ['llm.classify', 'notify.reply'],     // 缺了降级：规则判断 / 只记录不推送
  on: ['message.received', 'session.turn.ended'],
  config: z.object({ minConfidence: z.number().default(0.6) }).strict(),
}

export function setup(ctx: PluginContext) {
  ctx.provide('dev-dispatch.plan', { input: PlanIn, output: PlanOut }, async (input) => { … })
  ctx.on('message.received', async (e) => { … })
}

export async function start(ctx: PluginContext) { /* 可选：渠道类插件在这里起长连接 */ }
```

规则：

- **v1/v2 并存判别**：有 `kind` 字段 ⇒ v1（[ports.ts:16](../../../src/domain/ports.ts#L16) 不动）；`v === 2` ⇒ v2；两者并存或都无 ⇒ 启动失败。v1 插件收到的 ctx 仍是 `{config, log, register}` 三件，`plugins.test.ts:24-36` 手搓的 ctx 不会红。
- `needs` 启动时解析，**缺依赖直接失败**（一次报全部）；`wants` 缺失只 `warn` 并置 `ctx.has=false`，能力调用抛 `CapabilityMissingError`（不返回 undefined，避免降级静默）。只有 `needs` 参与拓扑排序，`wants` 不建边。
- **能力名与效果绑定**：内核按名字家族确定效果，插件不能把副作用能力声明成 `none`。
  - `session.*` → session，`notify.*`/`transport.*` → message，`doc.*` → doc，`task.*` → task。
  - 渠道插件只能实现 `transport.<slug>.*`（slug = id 去掉 `channel-` 前缀）与 `doc.<slug>.*`；其余自建能力必须用 `<slug>.*` 且 effect=`none`。
  - 内核保留前缀 `event./state./session./notify./judge./policy./task./transport./doc.`。
- 订阅在 `setup` 里声明，kind 必须在 manifest.on 里；一个插件对同一 kind 只能有一个 handler。插件不得 import 另一个插件，只能 `ctx.call/ctx.emit/ctx.on`。
- 平台命令与参数只出现在 `config/*.yaml` 模板里（沿用现有约定）。

### 4.3 内核-能力：提交 + 收据

**副作用能力不能同步返回业务结果**——这是本轮对抗评审改掉的关键点。要拿 `messageId` 去绑话题、要拿执行器 `sessionId` 去建会话，都改为「提交拿收据，结果走事件」。

| 能力 | 提供者 | 效果 | 语义 |
| --- | --- | --- | --- |
| `event.append` / `event.query` | 内核 | none | 追加/查询事件；查询供摘要场景按时间窗取数 |
| `state.get/put/list` | 内核 | none | 按插件 id 命名空间隔离的键值，替代直接写库 |
| `judge.classify` | 内核（规则；`llm.classify` 可选） | none | 规则命中不调模型；无判断器插件时只用规则 |
| `policy.check` | 内核 | none | 三轴闸：mode × effect × 风险（见下） |
| `workspace.list` | 内核 | none | 列允许根内的工作区（原 `#workspaceOptions`） |
| `session.start/post/stop/observe` | 内核 | session | 校验项目 → `allowRoots` → 登记 Work → 入 outbox；返回 `{receiptId}`。结果由 `session.started`/`effect.done` 带回 |
| `notify.reply` / `notify.push` | 内核 | message | 按 `target.channel` 解析 `transport.<id>.send`，入 outbox；返回 `{receiptId}`；结果由 `effect.done` 带回（含平台 `messageId`） |
| `task.open/claim/advance/merge/split` | 内核（工作项 reducer） | task | 工作项唯一写者；observe 档记 would-do；返回收据 |
| `claude.start/post/stop/observe`、`dsh.*` | 执行器插件 | none | 同步内部能力，只由 `session.*` 调用 |
| `transport.feishu.send`、`transport.dingtalk.send` | 渠道插件 | message | 同步内部能力，只由 `notify.*` 调用；参数来自配置模板 |
| `feishu.sendCard/patchCard/pin/downloadImage` | 渠道插件 | message | 控制台专用（话题、卡片、置顶、图片） |
| `feishu.readDoc/writeDoc`、`feishu.updateTodo` | 渠道插件 | doc | S2/S5 的回写能力 |

**提交与收据**：

- `capability_calls` 一行就是一张收据：`id`（receiptId）、`op_key`（唯一）、`name`、`effect`、`status`（would-do / submitted / done / failed）、`input_digest`、`input_head`（前 2KiB）、`outbox_id`、`result_head`、`error`、`duration_ms`。
- 同一 `opKey` 重复提交返回同一收据，不再入队（`INSERT OR IGNORE` + 查回）。
- `effect != none` 的调用一律 `submit`：落收据 → 入 outbox（`dedupe_key = opKey`）→ 返回 `receiptId`。投递成功后内核更新收据并追加 `effect.done`（结果含 `messageId`/`sessionId`）；重试耗尽追加 `effect.failed`。
- 只有 `effect = none` 的能力可以同步返回业务结果。
- **三轴闸**（`policy.check`，能力入口统一执行）：
  - mode：`observe` → 只记 would-do，不入 outbox；`suggest` → 落 `confirmations` + 发确认事件（P4a 接控制台按钮），确认后执行同一收据；`auto` → 直接执行。
  - effect：副作用必须带 `opKey`；没有直接拒绝。
  - 风险：`session.start` 额外校验 `allowRoots`；`auto` 档派工额外要求置信度 ≥ 0.9（沿用 [resolve.ts:19](../../../src/routing/resolve.ts#L19)）。
- 能力调用记审计；`effect != none` 的实现只能经内核调用；插件源码不得直接 `child_process`/`node:sqlite`（P1 起 doctor 静态扫描，P3 后收紧为启动失败）。
- 长等待不进能力与订阅：能力超时 30s；订阅 handler 超时 5s 可配；等人（选择题/授权）仍由问题表 + tick 的状态机驱动，不占用投递线程。

### 4.4 内核-事件：一份事件史

```ts
interface BusEvent<T = unknown> {
  seq: number                 // 全局单调，投递游标用
  id: string                  // 消息事件 = events.id；领域事件必须给自然键
  kind: string                // 'message.received' | 'session.turn.ended' | ...
  source: string              // 插件 id 或 'kernel'
  subject?: string            // 会话/工作项/文档 id（用于观测与分队列）
  at: string
  payload: T
  causedBy?: string           // 因果链：上游事件 id 或收据 id
}
```

- **只有一份事件史**：`event_log` 是唯一总线日志；原 `events` 表降级为「消息明细」（保留 `raw`，供旧查询与回放）。消息事件写入时 `events` 与 `event_log` **同一事务、同一 id**（`event_log.id = events.id`）；订阅者只读 `event_log`。不变式：每条 `events` 都有且只有一条 `event_log`；有测试与 doctor 检查。
- **id 规则**：消息事件用内容派生 id（[ids.ts:9](../../../src/kernel/ids.ts#L9)）；领域事件必须由调用方给自然键（如 `session.turn.ended:<sessionId>:<turnId>`），缺 id 的 `event.append` 直接拒绝——不拿时间戳/随机数当 id。
- **游标**：`subscriptions(subscriber, kind, cursor, enabled)`；新订阅默认从 `subscribe` 时刻的 `max(seq)` 开始（**绝不回放历史**），回放必须显式 `since:'beginning'`（只给测试/工具用）。
- **投递**：全局串行 tick（与今天 `chain` 的单写者语义一致），按 `(subscriber, kind)` 各自保序；单条失败退避重试（1s→60s，5 次），到顶进 `deliveries` 死信并**越过游标**，不卡后续。每个 handler 有超时；超时按失败处理。
- **积压**：滞后超过 `maxLag`（默认 5000）冻结该订阅并告警；恢复时最多补投 `maxCatchUp`（默认 200）条，超出则跳到当前 `max(seq)` 并记一条死信说明。
- **幂等**：投递是至少一次；副作用由收据的 `opKey` 唯一约束兜底，订阅者不需要自己造幂等键。handler 必须可重入：只读事件、写收据、发事件，不直接执行副作用。
- **事件种类（第一版）**：`message.received`、`card.action`、`session.started`、`session.turn.ended`、`session.question.asked`、`session.permission.requested`、`task.opened`、`task.claimed`、`task.advanced`、`task.merged`、`task.split`、`effect.done`、`effect.failed`、`doc.changed`、`todo.changed`、`schedule.tick`。
- 钩子回传改为：`hook-server` 只把 claude 的 Stop/Notification/Ask/Permission 转成事件；业务由场景订阅消费。

### 4.5 工作项与待办（P4a/P4c 才落地，P1 不建）

工作项是跨事件、跨多次执行的业务对象；`status` 只是投影，唯一写者是内核 reducer。

```ts
interface WorkItem {
  id: string                        // sha256(scenario|originKey)[:16]
  title: string
  scenario: string
  status: 'open' | 'claimed' | 'running' | 'done' | 'failed' | 'cancelled'
  revision: number                  // 乐观并发
  origin: { kind: 'event' | 'workitem'; id: string; at: string }[]
  bindings: { kind: 'session' | 'doc' | 'todo' | 'message'; key: string; hash?: string; url?: string }[]
  links: { parentId?: string; childIds: string[] }
  memberKey?: string                // 合并建议的内容派生键
  sessionIds: string[]
  steps: { seq: number; at: string; kind: string; detail?: string }[]  // append-only
  writtenSeq: number                // 回写水位
  writeback: { state: 'idle' | 'pending' | 'blocked-human'; lastError?: string }
  createdAt: string
  updatedAt: string
}
```

- **状态由 `deriveStatus(steps, lease, sessions)` 重算**：`open`（场景 open）、`claimed`（拿到租约）、`running`（`session.started`）、`done/failed`（`session.turn.ended` + 报告）、`cancelled`（只有人能取消，AI 只能报告失败）。
- **认领协议靠唯一约束**：`work_item_bindings(kind, key UNIQUE)`；同一待办被重复认领时 `INSERT OR IGNORE` 返回既有工作项，不新建。`leases(work_item_id PK, holder, token, attempt, heartbeat_at, expires_at)`：UPSERT 抢租约、token 校验心跳、过期回收 `attempt+1`，超 3 次转 `failed(lease-expired)`。
- **合并/拆分确定性落库**：模型只出建议；`merges(member_key UNIQUE)` 保证同一建议只落一次；拆分 id = `sha256(parentId|partKey)`；非法建议在 reducer 抛错、零写入。
- **回写**：`claimed` / `session.started` / `turn.ended`+报告 / 终态四个触发点只落 outbox 行；`dedupeKey = wb:<workItemId>:<seq>`；`writtenSeq` 水位保证不乱序；回写内容按 `steps[0..k]` 整段替换；写文档失败不影响工作项，退避 3 次后 dead 并在面板可见。
- **文档冲突**：认领时记 `hash=sha256(块文本+revision)`；回写前比对，不等则 `blocked-human` + `doc.changed` 要人确认。AI 不覆盖人写正文，只写自己的「进度」节（待确认的口径，见 §十三）。
- 表：`work_items`、`work_item_origins`、`work_item_bindings`、`work_item_steps`、`leases`、`merges`；`works` 增 `work_item_id`、`attempt` 两列（幂等补列）。

## 五、方案取舍

| 方案 | 判断 | 理由 |
| --- | --- | --- |
| A. 统一插件契约 + 能力/事件（本方案） | **选** | 直接满足 R1–R3；与 DSH 同源（Cordis 的服务/事件/注入），团队认知一致 |
| B. 继续在四类端口上加种类（`source-todo`、`scenario-*`） | 否 | 每加一类改内核四处，正是今天的问题；「场景」仍不是插件 |
| C. 引入 n8n / Dify 等工作流引擎 | 否 | 交接文档已否决：判断必须模型做且落表可回放，工作流引擎的编排在这里是负担 |
| D. fork `dsh-superagent` 改造 | 否 | 目标不同，且它自身执行器不插件化、工具清单硬编码、内核有 8 条平台直连——不重复它的债 |
| E. 只做「能力面」不做「事件面」 | 否 | 结果回传与待办进度都靠事件；只做能力会让场景继续被内核定时器驱动 |

**参考实现给出的正反两面**（本批隔离阅读的结论）：

- Super-agent 原型：`Trigger → Engine → Ticket → Assignment` 单一写者 + 角色 `Pick` 收口，比「Router 直接调 Worker」更难绕过授权；订阅是拉模式（`Thread.subscriptions`），没有 pub/sub API；工具是两套硬编码数组，执行器不是插件，内核仍有平台直连。→ **抄「单一写者 + 角色收口」，不抄「能力/执行器硬编码」**。
- DSH：约 100 个 Cordis 插件包组成一个 `dsh-base` bundle；`inject` 声明依赖、`Service` 提供能力、`ctx.on` 订阅事件、fiber 释放自动拆除效果；插件之间不互相 import。→ **这就是 R1–R3 的成熟参照**。
- 前身 `feishu-bridge-claude`：已经有场景插件清单（`core/ask/notify/permission/status/auto-reply` + `depends`/`services`/`hooks`）。lingcub 把它们收进了内核，新架构是把这一层补回来，并补上「持久事件 + 类型化能力」。

### 6.2 对抗评审 10 条与处置

| # | 评审结论 | 处置 |
| --- | --- | --- |

| 9 | P3 行为等价无基线；审计 30 条不是 32 | **接受**：P3.0 立金标（40 条输入快照 outcome+outbox+sessions/cards）；文档改「30 条已实现 + 15 条约定」（32 行中 28/29 不适用） |

### 6.3 计划必须改的三点（已写入第七节）

1. **幂等与效果收口进内核**：提交+收据、`opKey` 唯一、发件箱 `unknown` 恢复；订阅者不承担幂等。
2. **事件层一份史**：`event_log` + `subscriptions/deliveries`，订阅从创建时刻起投、绝不回放；新表幂等创建、不推版本。
3. **先立行为基线再搬**：P3.0 金标 + 审计脚本同步；tick 有「订阅者不得阻塞」的实现约束与测试。

### 2026-11-04 P3.7 删 `Pipeline` 前差异盘点

**仍由旧实现负责的路径**

| 路径 | 位置 | 状态 |
| --- | --- | --- |
| 消息入口与判断/派工 | `src/kernel/pipeline.ts` `ingest` / `dispatch_session` | 场景只接控制台命令；派工仍走旧 Pipeline |
| 开窗/选择卡（`#newwin`/`#attach`/`#resume`） | `pipeline.ts` `#startNewWindowFlow` / `#startResumeFlow` / `pick` 回调 | 未迁；回调解析在 `pipeline.ts:1250`、`1413` 附近 |
| 卡片构建 | `src/kernel/card-content.ts` | 仍是内核代码；场景只回文本 |
| 题卡/授权交互 | `pipeline.ts` 等待状态 + `runtime.ts` 钩子 | 场景只做只读回显，不能答题/批准 |
| 停/置顶/新窗命令 | `pipeline.ts` 命令分支 | `#stop`/`#new` 有交接；`#pin`/`#unpin`/`#help` 未迁 |
| 文档/待办动作 | `update_doc`/`create_todo` Action | 仍是占位分支，P4c 才实现 |
| 附件/图片落盘 | `pipeline.ts` 图片目录/附件处理 | 未迁 |
| 审计脚本 | `scripts/audit-parity.mjs` | 仍硬编码旧 `Pipeline` 符号，删 `Pipeline` 前必须改 |

**阻塞项（按先后）**

1. **消息入口双份**：source 插件把消息写进 `events` 后，`Pipeline.ingest` 同步处理；场景通过 `event_log` 异步消费。两者同时开机会双回。删 `Pipeline` 前必须先让「消息→判断→派工」完全走总线，或给入口加单一消费者开关。
2. **等待状态机能力化**：题卡/授权的「等答案」状态在 `pipeline.ts`，场景拿不到；需要 `session.answer` 能力 + 回调路由，才能迁卡片交互。
3. **卡片构建归属**：`card-content.ts` 必须挪到场景/渠道插件，否则内核仍认识飞书卡片结构。
4. **命令交接白名单**：现在只有 `status`/`stop`/`new`；`#pin`/`#unpin`/`#help`/`#attach` 等要逐条补，或一次性切「场景全量接管控制台命令」。
5. **生产切换**：`config/lingcub.yaml` 仍启用旧 sections；切换需要一次预演 + 回滚开关（不重启生产 daemon 的前提下无法验证）。

**结论**

P3 还不能删 `Pipeline`。可安全继续的是：先补 `session.answer` 与卡片构建迁移（1、2、3），再切入口单一消费者；P4c 文档/待办链路与 P3 收口互不阻塞，可并行推进。

**下一批**：P4c 飞书待办认领/合并/回写（独立于 P3 收口），或 `session.answer` 能力化。

### 2026-11-05 P2.6 修正：开窗改为执行器插件消费事件

**背景（用户指出）**

- 现有 `executor-claude` / `executor-dsh` 是 v1 端口插件，只 `start/read/post/stop`；claude 走 `--bg` 后台，不是本机终端窗口（`src/plugins/executor-claude/index.ts:2,22`、`executor-dsh/index.ts:20,79`）。
- 开窗由内核 `dispatch_session` 直接 `channel.sendCard` 发 ready 卡（`src/kernel/pipeline.ts:110-115`），内核知道飞书卡片形状；执行器只被当成起进程。
- 结论：P3 只完成了控制台命令迁移，开窗职责仍在错误层；此前“补频道建新话题能力”的方向作废。

**目标分层**

1. 场景/命令只提交 `session.open`（workspace/executor/prompt/话题/模式），不知道谁开窗。
2. 内核落 requestId、发 `session.open.requested` 事件，不直接开窗。
3. `claude` / `dsh` 执行器插件订阅事件，按配置打开**本机终端窗口**（或 headless），成功发 `session.opened`（handle/cwd/window），失败发 `session.open.failed`。
4. 内核消费 `session.opened/failed` 落会话、绑定话题、审计，发 `session.ready`。
5. 频道/场景插件消费 `session.ready` 才渲染飞书卡片/话题；卡片彻底移出内核。

**事件契约（草案）**

- `session.open.requested`：`{requestId, chatId, threadId?, rootMessageId?, executor, workspace, prompt, title?, mode:'terminal'|'headless'}`
- `session.opened`：`{requestId, executor, sessionId?, cwd, window?:{pid?,title?}}`
- `session.open.failed`：`{requestId, reason}`
- `session.ready`：`{requestId, sessionRowId, executor, sessionId?, cwd}`

**迁移切片（按参考项目契约）**

1. 事件契约 + `session.open` 能力 + 内核 pending 会话行/状态订阅（`opened/failed` → 会话行/`ready`），用假执行器插件测通，不碰真实终端。
2. `executor-claude` v2 化（先做）：`window=terminal|headless`；terminal 走「生成 UUID → 写映射 → `claude --session-id` 开窗 → 轮询会话表 → opened」；headless 保留现有 `--bg`。
3. 飞书频道/场景消费 `session.ready` 渲染 ready 卡；内核删 `sendCard`。
4. `executor-dsh` v2 化；resume/attach 适配。
5. 删旧 `dispatch_session` 开窗路径与 Pipeline 对应分支。

**风险/待定**

- `dsh` 交互入口是否有会话 id 预设参数未实测；没有就只支持 headless 的 post/read，terminal 仅开窗通知。
- 终端窗口关闭/进程退出与 Feishu 话题会话状态要对齐。
- Windows 开窗的 VBS/env 清理/wt 绝对路径要按参考项目移植，不能自己拼 `spawn('wt')`。
- 移动端没有终端窗口，headless 模式并存。

**平台事实（本机核对 + 参考项目）**

- `E:\Develop_E\feishu-bridge-claude` 已经实现「飞书话题 ↔ 本机 Claude Code 终端窗口」：
  - 开窗前生成 UUID，先把话题/消息映射写到该 UUID，再用 `claude --session-id <uuid>` 启动新窗口（`platform/win32/launch-claude.vbs`）；这是 Claude Code 的隐藏参数，help 里不列但实测可用。
  - 新窗口的 `SessionStart` hook 把 `session_id` 与 messaging socket/token 注册进会话表；桥接等到注册成功才回「创建成功」，超时关窗（`plugins/core/src/launch.js`）。

**参考项目给出的绑定契约**
