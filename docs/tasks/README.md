# 任务文档维护

- **文档角色**：研发任务台账、AI 的当前知识
- **读取时机**：开始任何新增、修复、排查、设计、实现、测试或续接任务时
- **更新条件**：任务登记、任务 ID、目录／命名、文档元数据、索引或维护流程变化时
- **事实来源**：用户确认的任务范围、[`INDEX.md`](INDEX.md)、当前任务文档、代码与自测、Git 历史、`CHANGELOG.md`

> `docs/tasks/` 是本项目研发任务的主账。开始任何任务前先检索（见第 1 节）；
> 命中已有任务时续接原任务 ID，只有确认不存在相关任务时才创建新任务。

**文档分工**：`README.md` 给使用者，`AGENTS.md` 给维护者（规范与约束），
[`../README.md`](../README.md) 是文档索引，`docs/000`–`004` 是设计，
`CHANGELOG.md` 是版本日志。**任务过程写进本目录**，不要污染上面这几份长期文档。

---

## 1. 开始任务前的固定流程

1. **先看索引**：[`INDEX.md`](INDEX.md) 是任务总览，一行一个任务（任务 ID、任务名、涉及模块、状态、概述），
   扫一遍就能判断有没有相关任务。命中即停，以任务 ID 为当前唯一检索键。
2. 索引里判断不出来时，按成本从低到高补检索：
   - **文件名**：任务文档名为 `YYYYMMDD-作者短名-随机码-任务名称.md`，按任务名或关键词做文件检索。
   - **全文检索**：仍不足以判断时全文搜 `docs/tasks/`，**只用返回的命中行**做判断；任务编号、根因词、模块名、文件名都可靠命中。
3. 定位到任务后读该文档的**具体小节**（如 `## 结论摘要`），不要整篇读。
4. 命中已有任务时，先读该行「相关文档」列里的材料，再更新原任务；不得因为换了会话、执行人、问题表现而重复创建任务 ID。
5. 只有目标、范围和验收标准都不能归入已有任务时，才创建新的任务 ID；已使用或已废弃的任务 ID 不得复用。
6. 已有任务只有索引行、尚无专项文档时，按本页规范在该任务 ID 下创建文档，不另建任务 ID。
7. **一个任务只有一份文档**，固定三段：**需求描述**、**技术设计**、**实施计划**；排查、验证、交接也写进同一份。
   **建文档在先，动手在后**：新建任务时先写需求描述、技术设计，以及实施计划的第一轮，再开始实现。
   **实施计划按轮追加**：每轮结束记下本轮做了什么、遇到什么问题、怎么修的、验证结果，不留到最后一次性补；
   这份逐轮记录就是追溯依据。既有文档不按新结构追改，续接时按需补齐三段。
8. 工作结束后同步更新任务文档的最后更新信息、相关材料和 `INDEX.md` 中的状态、结论及文档链接。

「任务」覆盖新增功能、缺陷修复、问题排查、产品／技术设计、实施计划、测试方案，
不以是否改代码作为登记条件。

## 2. 目录与文件命名

任务文档按**创建时间**归入月份目录。任务 ID 直接取文件名中从日期开始、到随机码结束的连续前缀：

```text
docs/tasks/
  README.md
  INDEX.md
  YYYYMM/
    YYYYMMDD-作者短名-随机码-任务名称.md
```

示例：

```text
docs/tasks/202611/20261103-dec27lee-WKD7Q23T-内核store与发件箱.md
```

任务 ID 示例：`20261103-dec27lee-WKD7Q23T`

规则：

- `YYYYMM` 是月份归档目录；文件名中的 `YYYYMMDD` 是任务创建日期。
- 任务 ID 格式为 `YYYYMMDD-作者短名-随机码`；文件名格式为 `任务 ID-任务名称.md`。创建日期只出现一次。
- 任务名称可以修正，任务 ID 和创建日期一经确定不得改变。
- 作者短名取创建任务时**本仓库实际生效的** Git 用户名（`git config user.name`），经规范化：
  英文转小写，中文转拼音小写，去空格和文件名非法字符，只留小写字母和数字。
  该字段表示首次创建人，不表示当前负责人。
  （参考项目的历史文件未做规范化，本项目按本规则执行。）
- 随机码固定 8 位大写字母和数字，字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`
  （排除易混淆的 `0`、`1`、`I`、`O`）。必须用安全随机源（`node:crypto`），
  不得用 `Math.random()`、时间秒数或分支内递增序号；生成后检查仓库内是否已存在，碰撞时重生成。
- 任务名称要能区分职责，不能只写「方案」「记录」「问题」；文件名不得含 Windows 禁止字符 `<>:"/\|?*`。
- 文档内容按需组织，通常包含：现状与目标、方案（涉及 `kernel`/`domain`/`routing`/`plugins` 哪一层）、
  改动清单与顺序、验证方式（`pnpm test` 覆盖到哪）、回滚、风险、完成判定。
  不需要的小节直接不写，不要为了凑模板写空标题。
- `README.md`、`INDEX.md` 是治理入口，不进入月份目录，也不套用任务文件命名格式。

## 3. 任务文档头部模板

每份任务文档从一级标题开始，紧接以下字段；时间统一用北京时间 `YYYY-MM-DD HH:mm:ss`：

```markdown
# 20261103-dec27lee-WKD7Q23T 内核store与发件箱

- **任务 ID**：20261103-dec27lee-WKD7Q23T
- **任务名**：内核store与发件箱
- **创建人**：Dec27-Lee
- **创建时间**：2026-11-03 17:00:00
- **最后更新人**：Dec27-Lee
- **更新时间**：2026-11-03 17:00:00
- **相关材料**：
  - [任务索引](../INDEX.md)
```

维护要求：

- 「任务 ID」必须与文件名中任务名之前的完整前缀完全一致。
- 创建人和最后更新人只写 `git config user.name`，**不带邮箱、不写 AI 名称或角色名**。
- 创建时间一经确定保持不变；每次实质修改正文、范围、状态、验收或关联事实时，更新
  「最后更新人」和「更新时间」。
- 「相关材料」至少链接 [`INDEX.md`](INDEX.md)；另有 PR、发布记录时再补，没有就只留索引一行。

## 4. 索引维护

[`INDEX.md`](INDEX.md) 只维护一张任务清单，每个任务 ID 一行：

- 任务 ID、任务名、涉及模块和当前状态；
- **相关文档**：该任务的文档路径，尚未建文档时填 `—`；
- 任务概述：**无论更新多少次，每条合计 ≤150 字**，覆盖当前稳定结论、风险与下一步；
  完整结论、验证证据写进任务文档（建议放在「结论摘要」节），索引行只留「这是什么任务、到哪一步」。

清单按任务 ID 中的 `YYYYMMDD` **倒序**排列，最近任务在前；同一天加到该段末尾。
续接任务只更新原行，不按最后更新时间移动或复制任务行。

新增或续接任务时：

- 先更新或确认清单中的同一任务 ID 行；
- **状态覆盖写，不追加**：续接时改写「当前状态」与「任务概述」，不新增行、不累积多轮结论；
- 新建、移动或重命名文档时同步更新该行的「相关文档」列；
- 状态必须描述真实研发阶段，不能只依据计划勾选项或单次测试；
- 发布与验收结论必须与当前代码、自测、Git 历史、`CHANGELOG.md` 交叉核验。
- **状态不记录 Git 流转**：不写「未提交／已提交／已推送」，提交痕迹由 Git 历史与 `CHANGELOG.md` 承担。
