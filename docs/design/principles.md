# 原则

违反以下任何一条的实现都不接受，即使它能跑。

## 1. 内核编排，插件实现

内核只做四件事：收事件、存事件、调用插件、把结果写进发件箱。
四类端口之外的能力，一律由插件提供。

**为什么**：这个系统唯一确定的事就是要不断加场景。内核里每多一行业务判断，将来就多一处不能改的地方。
**违反的后果**：改一个场景要动内核，内核测试全红，改动面失控。

## 2. 一切外部副作用走发件箱

起会话、发飞书消息、写文档、更新待办 —— 全部先落 `outbox` 表，再由投递器执行，成功才标记。

**为什么**：崩溃、超时、重复回调都会发生。副作用直接写在流程里，就必然出现「消息发了但没记录」或「记录了两遍」。
**违反的后果**：重复开会话烧钱，或者消息丢了没人知道。

## 3. 模型只做分类，路由由代码查表

模型回答「这是什么类型、值得做吗、建议给谁」；「给谁、用哪个执行器、能不能动这个目录」由代码查 `config/` 决定。

**为什么**：模型的判断不可复现、不可测、会漂。路由必须可重放、可断言。
**违反的后果**：同一条消息今天派给 claude，明天派给 dsh，没人能解释。

## 4. 默认 observe，执行要人确认

第一档：只记录，不动手。第二档：给建议，等你在飞书卡片上点「执行」。第三档：白名单内的低风险动作自动执行。

**为什么**：判断准确率未经验证之前，自动执行等于拿公司仓库试错。
**违反的后果**：一次误判就是一次错误提交。

## 5. 配置即事实

项目、工作区、执行器、预算、白名单 —— 全部在 `config/*.yaml`。代码里不出现路径、不出现人名、不出现仓库名。

**为什么**：这些是会变的事实，且变更的人是产品负责人不是开发者。
**违反的后果**：改一个工作区要发版。

## 附加：判断的四层分工

| 层 | 用什么 | 例子 |
|---|---|---|
| 确定性规则 | 代码 + `rules.yaml` | 白名单群消息、@我、私聊 |
| 语义判断 | 一次模型调用 + JSON schema | 这条是需求还是闲聊 |
| 领域知识 | `skills/*/SKILL.md` | 什么算「可开发的需求」 |
| 执行环境 | `config/projects.yaml` | 这个项目在哪、用哪个执行器 |
